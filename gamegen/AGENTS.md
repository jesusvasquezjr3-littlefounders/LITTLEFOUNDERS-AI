# AGENTS.md — gamegen (Arcade)

> Domain rules for this service. Root rules: [/AGENTS.md](../AGENTS.md). Context: [agent/core/CONTEXT.md](../agent/core/CONTEXT.md).
> **Engine spec (authoritative for the pipeline and for what Arcade generates):** [/GAME_ENGINE.md](../GAME_ENGINE.md) — §9 is this pipeline, §3–§5 are the contract it must satisfy.

## Mission

Generates concept-bound educational minigames for `games/` using **DeepSeek (author) + Qwen (judge) + Prism (art)**. Two things live in this package:

1. An Express `/health` service (internal). `src/app.ts` answers the health envelope **above** every guard and every optional dependency, mounts the internal-key guard on the `/api/v1` prefix (`timingSafeEqual` over fixed-width SHA-256 digests, **fail-closed** when `INTERNAL_API_KEY` is unset — `sha256('') === sha256('')` would otherwise make an absent header a valid match), and answers everything else with the `NOT_FOUND` envelope. There is still **no `/api/v1` route**: the guard exists so the first one cannot land unguarded, and nothing calls this service service-to-service today.
2. **Arcade**, a CLI pipeline (`npm run generate` → `src/cli.ts` → `src/pipeline/run.ts`) that turns a curated game catalog into `GameDocument`s in Vault. Arcade is **operator-triggered only** — never run by CI or any automatic process (`/AGENTS.md` sign-off rule, `agent/core/BOUNDARIES.md` #8: calling paid AI APIs in bulk and publishing are both boundary actions).

## Implementation status — 2026-07-30, branch `feat/game-engine`

Phases 0–6 of the Game Engine program are committed (`4b0b64f..d968a3e`), with an adversarial-audit fix pass in flight on top of them. The pipeline is **code, not a plan**. `src/` holds `env.ts` (Zod-parsed frozen config + `getConfig()`/`resetConfigCache()` + the lazy `require*Keys()` gates), `app.ts`, `index.ts`, `cli.ts`, `catalogCli.ts`, `catalog/` (schema, loader, check), `contract/` (the parity copy + `check.ts` + `registry.ts`), `pipeline/` (`plan`, `author`, `gates`, `simulateGate`, `judge`, `localize`, `images`, `publish`, `run`, `checkpoint`, `correctiveRetry`, `gamePlaybook`, `shapeExample`, `nonVisibleKeys`, `liveTelemetry`), `providers/` (`deepseek`, `qwen`, `openaiChat`, `retry`, `usage`, `errors`, `picturegen`) and `vault/` (`client`, `gamesRepo`, `telemetry`).

`npm test` is `catalog:check && contract:check && vitest run` — not vitest alone — and passes on this branch. The vitest suite covers the catalog + cross-catalog binding, the checkpoint queue, the stage-aware retry, the keyless `--dry-run`, the budget kill switch and ledger hydration, the provider chokepoint and Prism's status-as-retry-instruction, the localize string-freeze and its `NON_VISIBLE_KEYS` coverage, the winnability gate, publish, and `/health`. `contract:check` reports *29 files + 44 `core/types.ts` symbols + 10 `core/schema.ts` symbols + 2 character symbols + 1 substituted function*; `catalog:check` reports *18 blueprints across 9 topics, 0 errors, 7 warnings* (the tier-disagreement warnings the QA catalog raises on purpose — see its header comment).

Everything below describes shipped code **except** what the "Known gaps" section at the end names. Read that section before assuming a stage is end-to-end wired.

**No paid run has ever been executed from this package.** Not one DeepSeek, Qwen or Prism call has been made by Arcade; `games` / `game_documents` hold zero generated rows. Triggering one is the owner's decision under `agent/core/BOUNDARIES.md` #8, exactly like a Forge run.

## Approach decision — RESOLVED 2026-07-30

**DECIDED: parameterized prebuilt mechanics + LLM-generated JSON manifests.** Eight hand-written, deterministic game mechanics (code) are skinned and parameterized per instance by a generated `GameDocument` (data). Human sign-off given by the owner 2026-07-30; the decision is recorded in `ROADMAP.md` and specified in `/GAME_ENGINE.md` §1.

**REJECTED: fully generated HTML5 sandboxed games.** Three independent reasons, each disqualifying on its own:

1. **Unreviewable code surface aimed at children (§1.9).** Generated *content* can be moderated; a generated *program* cannot. Kid-facing output must pass moderation before display and a human publish gate — a novel program per instance means the thing a child executes was reviewed by nobody. "Sandboxed" is a containment claim, not a safety claim.
2. **No shared quality bar.** N generated engines means N feel-and-fairness implementations, N accessibility postures, N responsive behaviours (§1.11), N motion policies. With 8 hand-written mechanics there is exactly one of each, and improving `runner` improves every `runner` game ever generated, retroactively.
3. **Incompatible with the deterministic gate/judge pattern that made Forge work.** Generated code cannot be replayed server-side (so it cannot derive a reward — see the rewards invariant below), cannot be bot-tested for winnability before publish, and cannot be gated cheap-first before the paid judge. It would leave the client-reported score as the only reward signal — the exact thing this file forbids.

Extending the closed mechanic set is `/GAME_ENGINE.md` §12, not a re-litigation of this decision.

## Invariants that bite here

- **Every game binds to a learn/ concept — orphan games do not exist, and the link is DATA, not convention.** The blueprint carries `topic_path`; `validate` cross-checks it against `coursegen/curriculum/<course>/catalog.yaml`; publish stores the resolved `games.topic_id` FK. A game whose topic cannot be resolved must fail the run, never publish "unbound".
- **Rewards are SERVER-DERIVED BY REPLAY. A client-reported score is a claim, never a grant.** The client submits `{ seed, input_log }`; Core re-runs the mechanic's simulator over that log and derives the score itself (`/GAME_ENGINE.md` §6). The weaker posture — "the backend validates that the reported score is plausible" — was **rejected**: plausibility only rejects absurd numbers, so a *plausible fabricated* score would have been granted, and the bound it checks against is exactly the bound an attacker reads off the client. Replay has no such gap: an input log either reproduces the score or it is a `422 RESULT_REJECTED`. This is why every simulator must be pure and deterministic (§5) and why `gamegen/src/contract/` exists at all — **a mechanic the server cannot replay can never grant XP.**
- **Sandboxed output: the manifest never carries executable code and never names an external host.** Sprites/backgrounds are Depot URLs produced by Prism; SFX/BGM are ids from the closed vocabularies. No `<script>`, no data-URI payloads, no third-party CDN. Under the decided approach this is enforceable by Zod, which is half the point of the decision.
- **All AI-generated text and art shown to kids passes moderation (§1.9) — non-optional, three layers:** deterministic gates (forbidden-vocabulary per age tier × locale is a HARD fail), then the judge's `kid_safety` floor, then the blocking human publish gate. Arcade publishes `status='review'` and **never auto-publishes**.
- **Generated content ships in 3 locales** (es-MX authoring locale, then en-US + pt-BR from `localize`), and every chrome string the engine renders is an i18n key in all three (`/AGENTS.md` §1.8). Never a silent es-MX-only game.
- **No minor PII in any prompt.** Prompts carry the blueprint, catalog concept context, the age TIER and the character canon — nothing else. There is no per-child generation path; adding one needs explicit human sign-off against §1.9.
- **All AI output is Zod-validated against the copied `/GAME_ENGINE.md` contract before it is trusted for anything.** Never persist unvalidated model output; never relax a schema to make a generation pass (§1.14).

## Pipeline shape — as implemented (spec: `/GAME_ENGINE.md` §9)

Stage → module, so a rule below can be checked against the code that carries it: `validate` = `catalog/loader.ts` (called by `run.ts` before anything paid) · `plan` = `pipeline/plan.ts` · `author` = `pipeline/author.ts` · `gate` = `pipeline/gates.ts` (`runAllGates`, injected into author's retry loop AND re-run standalone as the final authority) · `simulate` = `pipeline/simulateGate.ts` · `judge` = `pipeline/judge.ts` · `localize` = `pipeline/localize.ts` + `pipeline/nonVisibleKeys.ts` · `illustrate` = `pipeline/images.ts` → `providers/picturegen.ts` · `publish` = `pipeline/publish.ts` → `vault/gamesRepo.ts`. Orchestration, the concurrency pool, the budget scaling and the stage-aware retry all live in `pipeline/run.ts`.

```
stages:            validate → plan → author → gate → simulate → judge → localize → illustrate → publish
checkpoint states: pending → planned → authored → simulated → judged → localized → illustrated → published
                   (+ 'failed' with failedFrom, + 'dry-run' for pristine slots only)
live stage labels: planning, authoring, simulating, judging, localizing, illustrating, publishing
run id namespace:  games-<courseSlug>-<ISO8601>     // NEVER collides with Forge run ids
telemetry marker:  generation_runs.params.kind = 'games'
```

Nine stages, **eight** checkpoint states: `gate` owns no state of its own because it is expected to run INSIDE the author stage's corrective-retry loop, the way Forge's gates run inside `write.ts` via `WriteInput.gateCtx` — so a gate failure is actionable feedback to the next attempt, not a dead slot. Write every gate message so a model can act on it: name the field, the expected value, the observed value.

- **Paid stages: `plan`, `author`, `judge`, `localize`, `illustrate`.** `validate`, `gate`, `simulate` and `publish` cost nothing. Keep the free stages cheap-first and ordered before the paid judge — letting cheap garbage reach a paid call is the mistake Forge's two-phase gate/judge split already paid for.
- **`--dry-run` spends NOTHING, structurally.** The short-circuit sits in `processSlot` BEFORE all five paid stages, `runGeneration` skips `requireGenerationKeys()`/`requirePublishKeys()`/`requireIllustrationKeys()` for dry runs, and only PRISTINE `pending` slots (state `pending` AND no `data`) get the `dry-run` marker — a slot carrying in-progress checkpoint data is counted as validated without touching the checkpoint, because `setSlotState` replaces `data` wholesale and marking it would wipe paid, judge-approved work. Regression pins: `src/__tests__/dry-run.test.ts` and `src/__tests__/keyless.test.ts`, which run with the API-key env vars deleted. (Forge's dry-run once only skipped publish — it paid the full generation bill while reporting that nothing was paid for. Do not rebuild that.)
- **The budget kill switch only exists if it PROPAGATES.** `checkBudget()` runs before every paid call and throws `BudgetExceededError`; `run.ts`'s `processSlot` catch rethrows it (and `isFatalProviderError` errors) instead of marking the slot failed, and the pool then stops scheduling new slots (published slots stay published, the rest stay resumable). A per-item `catch` inside a stage MUST rethrow it rather than degrading it to "skip this one". Forge's `illustrateSegments` swallowed it per target: a run that had already hit its USD cap kept walking every remaining image, paid for each, and shipped lessons with silently missing art while the cap read as enforced. Arcade's `illustrate` loops over sprite slots — the identical shape, so the identical trap. Pinned by `src/__tests__/budget-kill-switch.test.ts`, which also pins that the per-run cap is HYDRATED from the run's own `ledger.jsonl` (otherwise "per-run" is really per-invocation and bounds nothing across the resumes a long run needs) and that the cap scales as `max(absolute, slots × per-slot)`.
- **Every cost goes through the JSONL `UsageLedger`, or it is invisible to every guard.** Image spend sat outside Forge's ledger for months and was its largest uncapped cost.
- **`simulate` is the bot-play winnability gate — free, deterministic, and the reason a generated game is trustworthy.** `pipeline/simulateGate.ts` runs the mechanic's simulator headless (the parity copy in `gamegen/src/contract/`, whose bots come from `getMechanicBots()` in `contract/registry.ts`) against the authored document: the **`perfect` bot MUST reach `scoring.pass_score`**, the **`random` bot MUST NOT**, and the tick budget must hold. `explorer` additionally runs its reachability solver — an unsolvable world is a total failure no LLM judge catches. On failure the bot trace is corrective feedback for the next author attempt. No LLM is involved; it runs BEFORE the paid judge, and it is wired in TWO places (`freeGates`, inside author's corrective-retry loop and inside judge's `revalidate` hook) plus once standalone as the authority — because a revise cycle is exactly the edit that makes a target unreachable. Pinned by `src/__tests__/simulateGate.test.ts`.
- **`illustrate` runs on the es-MX document BEFORE the `localize` string-freeze.** Sprite URLs, `palette`, `background_url`, `sfx` and `bgm` then copy verbatim into en-US and pt-BR: **one image serves three locales**, a 3× cut in the dominant cost of mass generation. This is the ordering `coursegen/src/pipeline/run.ts` really uses inside its `reviewed → localized` transition; the stage list keeps Forge's stage NAMES for CLI/telemetry parity.
- **The `NON_VISIBLE_KEYS` twin skips CONTAINER keys, not just named leaves.** Consequence of the ordering above: `localize` must not translate `sprites`, `background_url`, `palette`, `sfx`, `bgm`, `config`, `mechanic`, `topic_path`, `image_slot`, `icon` or any id. This is a **different shape** from coursegen's field-name list, because sprite slots are arbitrary `Record<string, string>` keys — you cannot enumerate the leaves, you must skip the whole container. `pipeline/nonVisibleKeys.ts` implements it and its colocated `nonVisibleKeys.test.ts` (schema-derived, the twin of `coursegen/src/__tests__/nonVisibleKeys.test.ts`) plus `src/__tests__/localize-freeze.test.ts` prove both halves: no visible string escapes translation, and no non-visible key is translated. When it fails, add the key — never weaken the test. Forge learned this when a `mode: "typed"` enum came back as pt-BR prose and broke the contract.
- **Prefix-cache discipline: static-first assembly, retries APPEND.** DeepSeek's context cache is automatic and prefix-based (identical LEADING tokens bill ~120× cheaper on v4-pro; DashScope bills implicit hits at 20% of input). So every prompt puts byte-stable material first (playbook, hard rules, closed sets, mechanic shape, judge rubric-in-system) and per-game material last, never splices a conditional into a numbered list (renumbering changes every following byte), and corrective retries append feedback AFTER the original messages so attempts 2..N re-send an identical leading prompt. Read `cached_prompt_tokens` back from the ledger — a prompt change that tanks the cache-hit share is a cost regression even when quality holds.
- **`gamePlaybook.ts` is ONE module injected into BOTH the author and the judge prompt** (twin of `coursegen/src/pipeline/contentPlaybook.ts`). The schema and gates enforce CORRECTNESS; the playbook enforces VALUE. Injecting it in only one place means the author aims at a different bar than the judge rejects against — which is how you get mechanically-valid, boring content.
- **Judge rubric dimensions are `concept_fit, fun_agency, clarity, kid_safety, difficulty_fairness`** (1–5 + notes), on Qwen — a deliberately decorrelated provider from the DeepSeek author. `kid_safety` is a hard floor, not an average input.
- **`checkpoint.ts` is shared by concurrent slot workers**: its writes serialize through an internal queue. Never `writeFile`/`rename` the checkpoint path directly, and never "simplify" the queue away (Forge's pre-queue version crashed with tmp-file `ENOENT` races at concurrency 2). It also refuses to RESUME a run whose recorded `params` disagree with the current flags while any slot is already `published` — otherwise `isSlotDone` treats work produced under different parameters as finished and the run reports success without doing it. `src/__tests__/checkpoint.test.ts` + `stage-aware-retry.test.ts` pin the queue and the stage-aware retry (`failedFrom ∈ {judged, localized, illustrated}` resumes; everything else regenerates from scratch; the LAST attempt always forces a fresh draw).
- **Publish writes `status='review'` and there is no code path that writes `'published'`.** `vault/gamesRepo.ts` exports the module constant `GENERATED_GAME_STATUS = 'review'` and `upsertGame()` takes **no status argument** — that absence is the enforcement, not a convention. A regenerated game that a human had already promoted is downgraded back to `review` on purpose: new unreviewed content behind an old approval is unreviewed content. Pinned by `src/__tests__/publish.test.ts`.
- **Operator scripts load `.env` explicitly.** `package.json`'s `generate` script is `tsx --env-file-if-exists=.env src/cli.ts` and `dev` carries the same flag. Forge's `generate` and Echo's `narrate:all` both crashed on their very first real invocation for exactly this. Any new script that reaches `getConfig()` needs the flag. Note that `catalog:check` and `contract:check` deliberately do NOT carry it — they must never need a credential.

## Contract-copy parity rule (no workspaces)

`gamegen/src/contract/**` is a **copy** of `frontend/src/game-engine`'s pure simulation code, not a re-export — this repo has no workspaces (`/AGENTS.md` §1.2). What is copied, as `src/contract/check.ts` actually enforces it:

- **Verbatim (29 files):** `core/schemaBase.ts`, `core/rng.ts`, `core/mathd.ts`, `core/scoring.ts`, `core/replay.ts`, and **three** files per mechanic × 8 — `schema.ts`, `simulate.ts` **and `bots.ts`**. `bots.ts` is not optional here: `simulate` bot-plays a document with the mechanic's real bots, so a drifted bot gates a different game than the one a child gets. The bots left `simulate.ts` precisely because the browser must never receive them (`/GAME_ENGINE.md` §5, "Where the bots live"), and splitting the module without extending this list would have silently ended parity coverage of the exact code the gate runs.
- **Symbol-level (deliberately partial copies):** `core/types.ts` omits the React-only `MechanicViewProps` + `MechanicSlice` (44 symbols checked); `core/characters.ts` lifts only `CHARACTER_IDS` + `CharacterId` out of the character rig; `core/schema.ts` omits `parseGameDocument` (10 symbols checked). The symbol lists are DERIVED from the frontend file minus the declared exclusions, so a symbol added upstream and never copied fails the gate instead of passing unnoticed — including non-exported helpers such as `crossFieldIssues`, where the sprite-slot, category-reference and duplicate-id rules live.
- **One declared substitution:** the frontend's async `parseGameDocument` vs this copy's `parseGameDocumentSync` (Arcade holds every mechanic eagerly and must not await a chunk loader). Exactly three textual substitutions are applied to the frontend original before the normalized bodies are diffed; any *other* change — a reordered check, a dropped cross-field call — still fails.

Adjust **only** the relative import paths when re-copying: the frontend uses the `@/` alias with no extension, this package is `NodeNext` and every relative import needs an explicit `.js`. The normalizer strips imports, whitespace and semicolons, so that rewrite is not counted as drift. Keep `simulate.ts`, `bots.ts` and `schema.ts` free of any React import precisely so the copy is possible.

`npm run contract:check` is the gate and it is wired into `npm test`. Run it after ANY change to `frontend/src/game-engine/**/{schema,simulate,bots}.ts` or the copied `core/*` modules, **in the same commit**.

> **RUN THE RIGHT ONE.** `backend/` has its own `contract:check` for `backend/src/game-contract/`. Running that one and seeing "OK" says NOTHING about gamegen's copies — the mistake made on 2026-07-25 with the lesson contract, which let real drift sit unnoticed for a whole session. Both matter.
>
> **WHY DRIFT IS SILENT AND EXPENSIVE.** Zod objects STRIP unknown keys by default. When the frontend contract gains a field the copy lacks, the author dutifully emits it, the gate validates the document, and the field is DELETED — no error, no warning, nothing in the logs. On the lesson contract that shipped `count_objects` lessons as bare icons with zero pictures in all three locales. On a game manifest the same drift silently strips a `config` field the simulator needs, which the winnability gate then reports as an unwinnable game — you will debug the bot, not the copy.

## Curriculum catalog authoring

`gamegen/curriculum/<course>/games.yaml` is **human-reviewed content design**, authored separately from this pipeline code. This package only defines/validates its Zod schema (`catalog/schema.ts`) and cross-validates it (`catalog/loader.ts`, `catalog/check.ts`, entry point `catalogCli.ts`): slug uniqueness, closed-set membership, and **every blueprint's `topic_path` exists in `coursegen/curriculum/<course>/catalog.yaml`** — read from the repo root; the prior art for reaching across packages is `coursegen/src/contract/check.ts`.

One catalog exists today: `curriculum/first-lemonade-stand/games.yaml`, the **non-shipping QA catalog** twinned with Forge's QA course — 18 blueprints over 9 topics, ≥2 per mechanic across all 8, tiers 1–3 and difficulties 1–5 spread deliberately so a single run touches every simulator, every gate and every per-mechanic schema. Its 7 tier-disagreement warnings are intentional design (a consolidation game pitched a band easier or harder than the lesson that taught the concept); they are the design conversation, not a typo to flatten. No production course has a game catalog yet.

`catalog:check` reads `coursegen/` from the repo root, so it is **dev/CI-time only** — Railway deploys gamegen with `--path-as-root` and `coursegen/` does not exist in the production image. Nothing on a request path may call it.

Both gates are wired, not manual: `gamegen-ci.yml`'s path filters include `coursegen/curriculum/**`, `frontend/src/game-engine/**` and `frontend/src/components/characters/control/types.ts`, and `npm test` is `catalog:check && contract:check && vitest run`. A manual-only check would be a silent gap — a Forge catalog rename would break the binding in a PR that touches no gamegen file at all.

Never hand-edit curriculum YAML from this package's code — a `catalog:check` content finding is something to report to whoever authors that file, not to patch programmatically.

## Known gaps — verified 2026-07-30 against the code on this branch

Recorded here rather than omitted (`/AGENTS.md` §1.12.7). None of these is a reason to weaken a rule above; each is work that has not landed.

1. **The two telemetry modules are written but NOT WIRED.** `pipeline/liveTelemetry.ts` (`LiveTelemetry`, the `generation_runs_live` / `generation_heartbeat_snapshots` heartbeat) and `vault/telemetry.ts` (`ingestGameRunTelemetry`, `gameRunId()`, the durable `generation_runs` / `generation_slots` ingest) are complete ports of Forge's, but a repo-wide search finds **no import of either** — `pipeline/run.ts` never constructs a `LiveTelemetry` and never calls `ingestGameRunTelemetry`. Consequence, stated plainly: **an Arcade run today writes nothing to the shared telemetry tables**, so `/admin/generation` will show a game run as absent rather than as a run of kind `games` — even though Core's `adminData.ts`, the admin dashboard and `dataintel`'s game funnels all became kind-aware in the same commit. `run.ts` also composes its own run id inline (`namespaceRunId(...)`) instead of calling `gameRunId()`; the two agree on the `games-` prefix, so this is duplication rather than a collision risk. Wiring is a `run.ts` change, not a rewrite of either module.
2. **`TopicConceptContext` has no producer.** `RunOptions.topicContext` is a seam a caller can fill, but `catalog/loader.ts`'s `TopicRef` carries only `ageTier`, so nothing resolves the bound topic's `concept`, `learning_objective`, `key_vocabulary` or `prior_knowledge` from Forge's catalog. In a real run the only concept context a prompt carries is the blueprint's own `micro_objective` — correct, and §1.9-clean, but thinner than what Forge gives its author. The gap is documented at the type in `pipeline/run.ts`.
3. **There is no `coach` script.** `package.json` has `dev`, `build`, `start`, `type-check`, `lint`, `test`, `test:watch`, `generate`, `catalog:check`, `contract:check` — nothing else. `judge.ts` does write `runs/<run-id>/rubrics.jsonl` and `providers/usage.ts` writes `runs/<run-id>/ledger.jsonl`, so the raw material for a Forge-style offline coach exists; the report generator does not.
4. **Game audio assets do not exist and game audio is not done.** The manifest vocabularies (`GAME_SFX_NEW`, `GAME_BGM`) are closed and Zod-validated here, so generated content can only name known sounds — but the only files in `frontend/public/sfx/` are the same 9 lesson SFX. `frontend/src/game-engine/core/audio.ts` maps each new event name to the closest honest existing file or to `null` (`launch`, `explode`, `whoosh`, `alarm`, `engine` resolve to silence), and `GAME_BGM_ENABLED` is `false` with no loop shipped. A missing asset is a silent no-op; every game must stay fully playable and winnable with zero audio. Real assets are an owner decision (ElevenLabs one-offs vs licensed loops) and are the standing pending owner action — never describe game audio as complete.
5. **No paid run, and therefore no empirical cost figure.** The per-slot budget defaults in `env.ts` (`ARCADE_MAX_TOKENS_PER_SLOT=150000`, `ARCADE_MAX_USD_PER_SLOT=0.25`) are inherited from Forge's shape, not measured against an Arcade run. Re-check them against the first real run's ledger before sizing a large catalog — a cap that cannot fit the job is a bug, not a guard.
