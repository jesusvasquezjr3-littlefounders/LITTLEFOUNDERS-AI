# AGENTS.md — backend (Core)

> Domain rules for this service. Root rules: [/AGENTS.md](../AGENTS.md). Context: [agent/core/CONTEXT.md](../agent/core/CONTEXT.md).

## Mission

The main API and the **only** service the frontend calls. Owns auth session handling (against Supabase GoTrue), the 6-role model enforcement, families & guardian links, tasks & rewards, and profiles/avatars. Orchestrates internal services (Forge, Echo, Guardian, Courier) via `INTERNAL_API_KEY` service-to-service calls.

## Owns / does not own

- **Owns:** `/api/v1/*` public API, role middleware, family/guardian-link business logic, task assignment/rewards, profile & avatar persistence, orchestration of internal services.
- **Does NOT own:** schema & RLS (→ `database/`), content generation (→ coursegen), TTS (→ audiogen), identity verification itself (→ parent-id-check — Core only consumes its verdicts), email sending (→ email-server).

## Invariants that bite here

- Role checks server-side from the DB — never trust client-sent roles. Superadmin gate = `@littlefounders.ai` (also enforced in DB).
- A kid without ≥1 verified guardian link is a bug — creation flows must be transactional about this (/AGENTS.md §1.3).
- **A `kid` account and its guardian link are ONE operation, and the write order is the safety property (§1.3).** `POST /family/kids`: check the username first (the common rejection, before anything exists), create the auth user, write the VERIFIED `guardian_links` row, then grant the role. If the link fails the auth user is DELETED again and the failure is audited - a kid row without a verified link is a bug, not a state, so the account must not outlive the link. The role is granted last on purpose: a kid with no link and no role is inert, a kid with a role and no link is the forbidden state.
- **Signup SCREENS on a date of birth and then discards it.** Required by `SignupBody`, checked against `MIN_SIGNUP_AGE_YEARS` (13), never forwarded to GoTrue and never persisted - a test asserts the date does not appear in the outgoing body. Keeping it would mean collecting a second piece of personal data to justify not collecting the first. Under-age gets its own code, `AGE_RESTRICTED`, because the frontend has to explain the way OUT (a parent creates the account, the guest path keeps working) rather than show a generic rejection. The route previously assumed adulthood "by construction" from the `universal` role, which is a fact about our vocabulary and not about the person typing.
- **A child is created, never signed up.** GoTrue's `/admin/users` with `email_confirm: true` and a synthetic address on a `.invalid` domain (RFC 2606, unroutable by definition). The ordinary `/signup` path would demand an address we must not collect from a minor (§1.9) and then, with `GOTRUE_MAILER_AUTOCONFIRM=false` in production, park the account behind a confirmation email nobody can open. The address is DERIVED from the username so nothing stores it twice - which is why a kid's username is not editable.
- **`eu()` validates that its argument is a UUID; `es()` is the encoder for everything else.** Passing a username to `eu()` throws a ZodError out of the route as a 500 rather than returning a 4xx. That strictness is deliberate and correct - reach for the right one rather than loosening it.
- Envelope + /api/v1/ + Zod on every route (§1.6). Error codes → frontend `errors.api.*` keys.
- Child data: parent visibility invariant; nothing kid-identifying to third-party APIs (§1.9).
- External IO with timeouts; internal calls carry `INTERNAL_API_KEY`.
- **Admin email data is proxied through Core (§1.5) — never direct browser access to email-server.** Core's `/api/v1/admin/emails/*` endpoints call email-server's `/api/v1/logs` on the internal network and validate the response shape with Zod before forwarding. All admin query params are Zod-validated at the edge. Fetch calls carry `AbortSignal.timeout(10_000)`.
- **OWNED — email server proxy:** `EMAIL_SERVER_URL` + `INTERNAL_API_KEY` for service-to-service auth. Core uses `http://localhost:4005` outside production and `http://email-server.railway.internal:4005` in production when the URL is omitted.
- **OWNED — dataintel proxy:** `DATAINTEL_URL` (default `http://localhost:4008`) + `INTERNAL_API_KEY` for service-to-service auth. Core's `/api/v1/admin/intel/*` endpoints proxy to dataintel with JWT role verification (`admin`/`superadmin`), internal-key forwarding, and Zod response validation — same pattern as the email proxy (`/admin/emails/*`). The browser never calls dataintel directly.
- **Social login is Core-brokered (§1.5) — the browser hits Core's `/api/v1/auth/oauth/*`, never GoTrue's `/authorize` directly.** `OAUTH_PROVIDERS` is the code allow-list (Google today); Core builds the GoTrue authorize URL with `redirect_to=<FRONTEND_URL>/auth/callback`. *Enabling* a provider is GoTrue config (`GOTRUE_EXTERNAL_<P>_ENABLED`/`CLIENT_ID`/`SECRET`), not a code change; `GET /oauth/providers` reflects what GoTrue reports enabled, so the frontend button self-hides until credentials exist. **`PROVIDER_AUTHORIZE_PARAMS` in `services/gotrue.ts`** adds provider-specific extra query params GoTrue forwards verbatim to the provider's own authorize URL (verified live via the raw `location` redirect header, not assumed) — Google gets `prompt=select_account` so a browser holding one Google session still gets the account chooser instead of silent auto-login; add a provider's own entry here rather than a generic default, since the equivalent param differs per provider. Route table + go-live steps: `README.md` "Social login".
- **Trust exactly one proxy hop.** `app.set('trust proxy', 1)` — Core runs behind Railway's single edge proxy, so rate limits must key on the real client IP (leftmost untrusted `X-Forwarded-For`), not the proxy address. `true` (trust-all) would let a spoofed header bypass the limiter; `0`/unset lumps every client into one bucket.
- **Middleware order in `src/app.ts` is load-bearing — do not reshuffle it.** `helmet` → `GET /health` → `cors` → `globalRateLimiter` → `express.json`. `/health` is mounted ABOVE the limiter because liveness must not depend on Redis being reachable and must not spend the caller's 200-req/15-min budget (the platform polls it continuously) — below it, a Redis outage failed the healthcheck and took Core down over a degraded *rate limiter*. `cors` sits above the limiter because a 429 is a response the SPA has to be able to READ: without `Access-Control-Allow-Origin` the browser discards the `TOO_MANY_REQUESTS` envelope and the user gets an opaque network error instead of "slow down" (it also lets preflights short-circuit 204 without consuming budget).
- **Rate limiting FAILS OPEN — `passOnStoreError: true` on both limiters (`middleware/rateLimit.ts`).** It is an availability control, not an authorization control: a store error lets the request through unmetered instead of 500ing. Fail-closed (the default) turned any Redis blip into a total outage on every route. Corollary: nothing that must hold when the limiter is bypassed may live in the limiter — it belongs in auth/role middleware or in RLS.
- **Redis is NOT a boot dependency — `listen()` opens first and `connect()` runs in the background (`src/index.ts`).** Do not "tidy" this back into an `await` before `listen()`: node-redis applies its reconnect strategy to the INITIAL connect too, so `connect()` against an unreachable server neither resolves nor rejects. Awaiting it left Core with no listener at all, the `catch`'s `process.exit(1)` unreachable, and Railway's ON_FAILURE restart never firing because the process was still alive.
- **`requireInternalKey` compares fixed-width SHA-256 digests, never the raw strings** (`middleware/auth.ts`; the same fix landed in all seven services). The old guard pre-checked JS string `.length` before `Buffer.from()` — `.length` counts UTF-16 code units, `Buffer.from()` yields UTF-8 bytes, so an equal-character-length key holding any byte ≥ 0x80 produced a longer buffer and `timingSafeEqual` THREW `RangeError`, surfacing as a 500 (HTML, ahead of the envelope handler) instead of a 403 envelope. Digests also remove the key-length side channel. Core is the caller side today: the helper is exported but currently mounted on no Core route.
- **Lesson grading is SERVER-AUTHORITATIVE — never trust a client-reported score or XP.** `POST /learn/lessons/:id/grade` and `/complete` are the only writers of `lesson_segment_attempts` / `lesson_progress` / `learning_stats`; the client submits a raw answer and Core alone decides the score, using `lesson_documents.answer_keys` (service-role only, no client can ever read it) and the graders in `src/lesson-contract/`.
- **A CAP ENFORCED BY READ-THEN-WRITE IS NOT A CAP.** Found by adversarial review, 2026-08-30 (CRITICAL): `POST /tutor/segments/:segmentId/grade` used to read "XP earned today", compute `min(requested, cap - earnedToday)` in application code, then write the result with a separate, unconditional PATCH. Two concurrent grade requests for the same learner both read the same stale total before either write landed, so both spent the full remaining cap — 20 XP awarded against a 10 XP remaining budget, reproduced. Core has no documented single-replica constraint (unlike Oracle — `oracle/AGENTS.md`), so an in-process lock cannot close this under horizontal scaling, and the cap spans every `tutor_sessions` row for a user on a given day — a span a row-level conditional PATCH (the `ended_at=is.null` pattern `closeTutorSession` uses) cannot express. Fixed with `award_tutor_xp` (migration 0055): the read, the cap arithmetic and the write happen inside ONE `SECURITY DEFINER` Postgres function, serialized with `pg_advisory_xact_lock` keyed on the learner — correct under any number of Core replicas, because the lock lives in the database. The general shape: whenever a cap or a total spans MORE than one row a single conditional `UPDATE` can guard, the atomicity has to move into the database (an RPC, or an explicit transaction), not stay split across a read call and a write call in Node — no amount of care in application code closes a race across two separate network round trips. The same review also found the route paying a segment's own XP fresh on every grade call with no memory of what that segment had already earned — a replayed grade request (a retry, a double-tap) paid the same segment's XP again each time. Fixed by capping each call's award at `baseXp - row.xp_awarded`, so a segment can never earn more than its own listed worth no matter how many times it is graded, while a genuine second attempt that improves the score still earns the delta.
- **A FORMAT GUARD IS NOT AN IDENTITY GUARD.** `PUT /tutor/preferences`'s nickname regex (`/^[\p{L}\p{N}][\p{L}\p{N} '_-]*$/u`) only ever excluded punctuation, not being a real name — it allows spaces, so a clean two-word name with no comma or period sailed through untouched, even when it was literally the learner's own `display_name`. Found by adversarial review, 2026-08-30 (HIGH): nickname is /ORACLE.md §4.1's "only name-shaped value that may travel" into the third-party model, and the existing rejection test (`'Ana Vasquez, Jr.'`) only proved the comma was excluded, never that a real name was. Fixed by cross-checking the submitted nickname against the caller's own profile `display_name` at the route (`looksLikeRealName`, word-based so a bare surname is caught the same as the full name) — the one place both values are ever in hand together. A regex that rejects malformed INPUT says nothing about whether well-formed input is the wrong VALUE; when a field is disallowed from being someone's real identity rather than merely disallowed from containing certain characters, the check has to compare against that identity, not just describe a character class.
- **READ-MODIFY-WRITE: any read whose result is written back MUST distinguish "upstream did not answer" from "zero".** `supabaseRest`'s `rest()` returns `null` for ANY non-2xx, network error or unparseable body — the failure and the empty answer look identical unless the caller keeps them apart. Display-only readers may collapse `null` into a zeroed default (`getLearningStats`, `getLearningStatsByUserId`); a reader that feeds a write may NOT. `getLearningStatsForUpdate` therefore returns `LearningStatsForUpdateRow | null` and `POST /learn/lessons/:id/complete` answers 502 on `null` rather than computing the update from assumed zeros. Collapsed into `ZERO_STATS`, one transient PostgREST failure made the following PATCH write deltas-from-zero back and silently erase the learner's `xp_points`, `minutes_learned`, `lessons_completed`, `streak_days` and `longest_streak` behind a 200 — and `minutes_learned` plus both streak columns exist nowhere else, so the loss is permanent. Regression test in `src/__tests__/learn.test.ts`. The rule holds for every future accumulate-and-write-back path, not just this one.
- **`src/lesson-contract/` parity is a standing invariant, not a one-time copy.** It mirrors `frontend/src/lesson-engine/{core/scoring.ts, core/types.ts (trimmed), families/*/grade.ts}` because the platform has no npm workspaces (/AGENTS.md §1.2) — Core cannot import the frontend package directly. Any edit to a frontend grading validator MUST be mirrored here in the same commit; `npm run contract:check` enforces this and is a pre-commit gate (§5) whenever either side changes.
- The course/lesson unlock rule (locked/available/current/passed, COURSE_ENGINE.md §2) is computed in exactly one place — `src/services/unlockRules.ts` + `courseTree.ts` — and never re-derived by the client.
- **A NEUTRAL FALLBACK MUST NOT ALSO ERASE WHY IT FIRED.** `POST /:courseSlug/intake`'s call into Oracle's `placementIntake.ts` correctly lands on a safe neutral prior when the learner's own text is flagged (self-harm, personal data, injection) — but until this fix, that fallback was byte-identical to Oracle simply being unreachable, found by adversarial review 2026-08-30 (HIGH). The FIRST exchange a learner has with the Tutor system produced zero signal, anywhere, that something concerning had been typed. Fixed by threading a `flagged: {category, severity} | null` field from Oracle through `services/placementIntake.ts` to this route, which now `console.error`s it with the caller's own `user.id` attached — the CLIENT response is unchanged (a child is never told their words were flagged, matching every other safety response). Full context: `/ORACLE.md` §4.1b. Explicitly left open: whether this belongs in a guardian-visible record — `tutor_safety_flags` needs a `session_id` this flow has none of.

## V4 — learner memory (2026-08-29)

- `learner_memory` is written ONLY through `writeLearnerMemory` (tutorData.ts), which pairs every store change with an append-only ledger row (actor, session, before/after hashes). A store write without its ledger row is logged as an ERROR — that pairing is the compensating control for auto-write.
- The brief read (`getLearnerMemory`) degrades to "no brief" on failure by design: it improves a session and must never block one. Do not make it load-bearing.
- `search_tutor_turns` is a service-role-only RPC scoped by user id; the `/internal/recall` endpoint must always pass the SESSION'S OWN user id, never a client-supplied one.
