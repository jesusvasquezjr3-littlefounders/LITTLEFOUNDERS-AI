# backend (Core)

> Part of LittleFounders v2. Read [/AGENTS.md](../AGENTS.md) first; domain rules in [AGENTS.md](AGENTS.md).

**Mission:** Main API — the only service the frontend calls. Auth, roles, families, guardian links, tasks, profiles; orchestrates internal services.
**Port (dev):** 4000 · **Deploy:** Railway

```bash
npm install
cp .env.example .env   # fill values (local Supabase secrets live in database/supabase/docker/.env)
npm run dev
npm test
npm run contract:check         # BOTH parity gates below (also runs as part of `npm test`)
npm run lesson-contract:check  # lesson-contract/ vs frontend/src/lesson-engine
npm run game-contract:check    # game-contract/  vs frontend/src/game-engine
```

**Social login (Google) is LIVE in production (2026-07-20)** — Core brokers the GoTrue provider flow through the two `/oauth` routes above (the browser only ever talks to Core, §1.5); the frontend `/auth/callback` route consumes the returned token fragment. The Google Cloud OAuth client is "LittleFounders v2 (GoTrue)" (project `littlefounders-auth`); GoTrue holds `GOTRUE_EXTERNAL_GOOGLE_ENABLED/CLIENT_ID/SECRET/REDIRECT_URI`. Verified E2E: button → Google → GoTrue → `/auth/callback` → session; OAuth users get their `display_name` from Google metadata (migration 0011) and start `universal`. The authorize URL always adds `prompt=select_account` for Google (`PROVIDER_AUTHORIZE_PARAMS` in `services/gotrue.ts`) — verified via the raw redirect header that GoTrue forwards it straight to Google, so a browser holding one Google session still shows the account chooser instead of silently reusing it. Adding Discord/Facebook later = extend the `OAUTH_PROVIDERS` allow-list + enable the provider in GoTrue + give it its own `PROVIDER_AUTHORIZE_PARAMS` entry if it needs one; no shape changes.

**Game rewards are SERVER-REPLAYED — do not "simplify" this into trusting a client score.** `POST /api/v1/games/:gameId/complete` accepts a `seed` and an `input_log` and *no score*, because the score is not the client's to report: Core re-runs the mechanic's deterministic simulator (`src/game-contract/`) over that log and the number it derives is the only one that reaches `game_attempts` / `game_progress` / `learning_stats`. The whole determinism contract (GAME_ENGINE.md §5 — integer 50 ms ticks, a seeded mulberry32 PRNG, only IEEE-754-exact arithmetic, `core/mathd.ts` instead of `Math.sin`/`cos`/`pow`) exists to make that replay bit-identical between the browser's V8 and Node's, so an honest player's run reproduces exactly and a forged one cannot. `replayGame` validates the log *before* initialising the simulator and short-circuits on the first violation, so a rejected attempt never produces a partially-credited state; the caller turns that into **422 `RESULT_REJECTED`** and grants nothing. A mechanic Core cannot simulate (an id this release has not implemented — `getMechanic` returns `null` rather than throwing, `src/game-contract/registry.ts`) takes the same 422 path: refusing to reward a run we cannot re-derive is correct, and granting the client's claimed number instead would be exactly the hole the replay path exists to close. This is the same posture as lesson grading (`lesson_documents.answer_keys` never leaving the service-role boundary) applied to a real-time loop: **any future edit that lets a client-supplied score reach a write is a security regression, not a refactor.**

## Notes

- JWTs are verified locally (HS256, `SUPABASE_JWT_SECRET`) — no per-request GoTrue round-trip.
- Request bodies are capped at 64 kB (`express.json({ limit: '64kb' })`), with two deliberate exceptions that carry their OWN parser and budget: `/api/v1/events` (beacon batches, mounted above the global limiter) and `/api/v1/games` (its `POST /complete` body carries an input-log array). Raising the global cap for either would hand every other route the same headroom; `input_log` is additionally length-capped in Zod against the sidecar's `max_events`, so the parser limit is a backstop, not the control. The envelope error handler answers with the HTTP status the thrown error carries (`err.status`/`err.statusCode` — body-parser attaches one; a `MulterError` is mapped to 400 by name): 413 → `PAYLOAD_TOO_LARGE`, any other 4xx → `VALIDATION_ERROR`, everything else → 500 `INTERNAL`. It used to flatten every client mistake into 500, telling the caller "we broke" when their body was simply malformed or oversized.
- Service-role PostgREST writes are reserved for what RLS deliberately closes to clients: role grants, `parent_verifications`, `audit_logs`, follower/following/blocked list hydration (reading OTHER users' profiles/avatars/roles).
- The ID photo is forwarded in memory to Guardian and never persisted here either. The same in-memory-then-discard posture covers a game's raw `input_log`: it is replayed to derive a score and dropped, and `game_attempts.stats` keeps derived aggregates only. A tick-resolution behavioural trace of a child at play is precisely what COPPA-minded minimalism says not to retain, and no reward decision needs it (GAME_ENGINE.md §11).
- Parent visibility into a kid's GAME activity is an invariant, not a setting — there is no toggle that hides it from a verified guardian. It rides the same guardian-link check as lesson visibility (`is_verified_guardian_of` in 0027's RLS, re-verified in the route before any service-role read). This is separate from `analyticsConsent`, which gates *telemetry* (`game_start` / `game_complete` insights are fire-and-forget behind the existing fail-closed consent gate), never a parent's view of their own child.
- `learning_stats` (xp/minutes/lessons/streak) is system-written only — exactly TWO routes mutate it, `POST /api/v1/learn/lessons/:id/complete` and `POST /api/v1/games/:gameId/complete`, and only by an XP delta / minutes / streak each computes itself from a server-derived score. `lessons_completed` is incremented by the lesson route alone: a game must never touch it, because `stats.lessons_completed === 0` is how Core asserts "first lesson ever", and it also feeds course progress, the parent dashboard and every `dataintel` funnel. Both routes answer 502 rather than writing when the stats read does not answer (§1.14).
- Error codes new with the Game Engine: `GAME_LOCKED` (403) and `RESULT_REJECTED` (422). Like every code in this service they map 1:1 to frontend i18n keys — `errors.api.GAME_LOCKED` and `errors.api.RESULT_REJECTED` exist in all three locales (§1.6/§1.8).
- Lesson grading is SERVER-AUTHORITATIVE: `backend/src/lesson-contract/` is a parity-checked copy (`npm run contract:check`) of the frontend's pure grading validators (`frontend/src/lesson-engine/{core/scoring.ts,core/types.ts (trimmed),families/*/grade.ts}`) — no workspaces (/AGENTS.md §1.2), so Core cannot import them directly. `lesson_documents.answer_keys` never leaves the service-role boundary; `POST /grade` re-attaches the server-only answer key to the client-safe segment and grades with the SAME validators the frontend ships, so scores can never be forged client-side.
- `backend/src/game-contract/` is the second parity-checked copy, on the same footing as `lesson-contract/` and for the same no-workspaces reason: it mirrors the frontend's pure simulation code (`frontend/src/game-engine/{core/types.ts (trimmed), core/rng.ts, core/mathd.ts, core/replay.ts, mechanics/*/simulate.ts, mechanics/*/schema.ts}`) so Core can re-derive a score without importing the frontend package. Any edit to a frontend simulator or mechanic schema MUST be mirrored here in the SAME commit — `npm run game-contract:check` enforces it and runs inside `npm test`. Its one non-copied file is `registry.ts`: the frontend registry is async so eight mechanics never become one bundle, while Core needs a synchronous, React-free lookup inside a request handler; an unimplemented mechanic is `null` there, never a throwing stub, so a forward-compatible document degrades to a refusal instead of a 500.
- The course/lesson unlock rule (locked/available/current/passed) is computed in exactly one place: `backend/src/services/unlockRules.ts` + `courseTree.ts`, consumed by all four `/learn` content routes. The client never re-derives it (COURSE_ENGINE.md §2).
