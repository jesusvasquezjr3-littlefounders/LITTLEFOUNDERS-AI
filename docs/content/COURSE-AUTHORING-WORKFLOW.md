## Deliverable and completion contract

The separate Financial Education [production sequence design](../../coursegen/curriculum-design/financial-education/lesson-sequence.json) defines 294 slots: 236 teaching objectives, 46 reserved retrieval lessons and 12 integrated capstone objectives. This includes an explicit payment-direction bridge before distinguishing received and promised money. Rebuild it with `node coursegen/curriculum-design/financial-education/build-sequence.mjs`. Its sources are individually authored objectives and proposed lesson-level dependencies, not reskinned lesson templates. The checker rejects missing domains, unresolved or forward dependencies, duplicate objective text and missing or premature retrieval. These checks do not prove semantic uniqueness or instructional sufficiency. The [nine opening briefs](../../coursegen/curriculum-design/financial-education/opening-briefs.json) now state misconceptions, worked reasoning, supported practice, independent transfer and scorer limits, with verified draft shared KC mappings. This planning format is intentionally not a runtime course blueprint. The complete-source artifact described above supplies the authored lessons, mappings and localized plans; the objective inventory alone is not playable content or evidence of learning.

Distinguish a calibration corpus from a production curriculum. Set `publication_intent` to `calibration-only` for test lessons and to `release-candidate` only for the separately designed production curriculum. Missing intent also blocks live publication and release attestation. Dry runs remain available for calibration. The current 36 Financial Education lessons are exclusively a calibration set; the owner's target is a broad introductory curriculum of hundreds of coherent lessons, generated after the shared system has been refined. A green calibration report does not satisfy that target or authorize mass generation to skip the same quality gates.

The calibration found that individually valid titles, prompts, scenes and options can still overload their combined mobile screen. Budget them together with the Mentor label and controls: first-view limits are 40 words in English and 50 in Spanish/Portuguese (25 and 32 for ages 6–9). Leave room for interface text; these numbers are not a per-field allowance or a substitute for rendered verification. When shortening, preserve every required amount, date, unit and assumption on the current board. Do not move essential information into optional help or audio. Recheck that the shortened question and options still form a coherent task. These rules are also supplied to Forge through `SHARED_INSTRUCTIONAL_RULES`.

A course consists of a declared, bounded competence scope; a prerequisite graph; ordered units; teaching lessons; independent retrieval; integrated applications; authored localized plans; and reproducible verification evidence. A lesson count alone is not completion. Do not label a foundation course as all financial knowledge or claim measured learning from successful compilation.

The production editorial pass adds two mandatory authoring practices. Every rejected option must express a plausible misconception about the current decision, not an unrelated preference or absurd distraction; use two meaningful options when a third cannot earn its place. Independently attempt to justify every option from the visible facts in every localization. Explicitly state opening balances, available funds before a deadline, positive-rate assumptions and complete payment schedules where the conclusion depends on them. Unknown value is not proven poor value. Teach a procedure before its first graded use; a transfer must assess the declared skill through a different decision, not merely replace the numbers. These rules are shared through `SHARED_INSTRUCTIONAL_RULES`; prose review remains necessary because schema and arithmetic checks cannot prove them.

Use `coursegen/src/v2/courseBlueprint.ts` for the course and `plan.ts` for lessons. Each skill maps to the existing shared KC graph and must explicitly include every required shared prerequisite. A course may declare additional contextual prerequisites, but those must also exist, be taught earlier and match the lesson contract. Shared edges represent required competencies, not the incidental order of one course. Add narrowly defined draft KCs when the old nodes would credit unrelated knowledge; never activate them or reset calibrated parameters as a side effect of authoring. Course building does not create a second learner-mastery store.

1. Research authoritative competence frameworks and current subject claims. Define observable outcomes, audience, locale assumptions, excluded scope and sources. Convert framework coverage into a prerequisite sequence; do not copy a framework table as the teaching order.
2. Write the complete blueprint before declaring the course complete. Allocate each skill an introduction and later independent retrieval with at least one intervening lesson. Include integrated capstones. Structural spacing is not elapsed-time spaced repetition.
3. Author one concept per teaching lesson: useful problem, explicit worked reasoning, a supported action, independent practice, fresh-context transfer and explanatory feedback. Consolidation and capstones retrieve previously taught skills. Six to ten exercises and three to five minutes are design targets, not padding quotas or measured duration claims.
4. Choose the engine representation that exposes the relationship. A ledger should represent money movements; a percentage grid should show the share; a simulator must name its assumptions and limits. Do not force interaction variety or use a displayed solved model as an independent assessment.
5. Write the expected reasoning before the key. Check every distractor against the visible scenario; prefer plausible misconceptions over absurd alternatives. A correct option may not be the longest, always first, or inferable from metadata. All required facts must be visible without optional audio or a remembered earlier screen.
6. Recompute numeric answers from displayed inputs. `numeric_proof` carries a bounded private expression for numerical choices; Core independently checks native numeric-board models. These checks do not prove that a chosen financial model or qualitative recommendation is appropriate. Review prose calculations, worked examples and all omitted assumptions separately.
7. Review exactly what the scorer proves. A choice-only scorer does not validate a written reason. A balance target does not establish the order of transactions. Feedback must describe the checked action. Optional `choice_hints` must cover every option, including neutral guidance for an accepted option, so membership never exposes the key.
8. Compile the entire course and inspect all findings. Fix failures in the authoring source, regenerate, and preserve review items. A failed build emits no release corpus and invalidates stale files, including after parse errors.
9. Exercise the actual player with correct and incorrect answers, retry, help, keyboard, completion, mobile and desktop in each locale. Inspect text contrast, full-screen copy load, text fit and proportions. A valid JSON document and a generic fixture browser test are insufficient.
10. Record authored, technically verified, editorially reviewed, novice-tested and released statuses separately. Use the repository release process and existing retention/learning measurement. No synthetic test certifies habits, real-world transfer or return visits.

## One authoring interface, three execution choices

Direct coding agents write the same plan and blueprint files that Forge accepts. They do not need a provider API. The compiler exports `authoring-packets.json` containing bounded course context, the instructional contract, engine payload facts and the same messages used by Forge. These are private authoring artifacts, not player payloads.

Paid Forge authoring (`v2:author` without `--dry-run`) requires the instructional contract, `--blueprint`, and the existing owner-authorized spend ceiling. Provider output is not trusted because it came from the approved prompt: the same compiler, Core scorer and review process judge it. No paid generation was used for the recovery catalog. Skill invocation does not authorize spending or publication.

Codex and Claude use the repository skill `course-authoring`; `financial-lesson-authoring` adds the financial scope and source guidance. Neither skill claims a human review occurred.


From `backend/`:

```powershell
npm run forge-v2:check -- ../coursegen/runs/solid-course/documents.json
```

The reference has 36 adult foundation lessons, 27 separately tracked draft skills, eight units, seven consolidation lessons and two capstones in English, Mexican Spanish and Brazilian Portuguese. This is 216 distinct graded exercises and 648 localized instances, not 648 distinct instructional designs. It is not a hundreds-lesson catalog. A separate synthetic 360-lesson test measures graph handling only; it is not evidence of content quality at that volume.

From `frontend/`, run `npm run review:course` to inspect the compiled reference course at `http://127.0.0.1:5197/scripts/course-review/index.html`. Select lessons and locales, answer incorrectly, retry and complete the real player. For a different compiled corpus, set `COURSE_REVIEW_FILE` to its absolute `documents.json` path before starting. Restart the server after recompilation. This explicit development config serves public documents and uses the canonical Core scorer locally; answer keys remain on the server. It records no learner progress, publishes nothing and is not an authenticated production journey. The normal app configuration and production entry do not include this tool.

The source modules are an editable representation of authored storyboards, not a template farm or an alternative runtime. `build-source.mjs` writes source plans and draft KC seed definitions; `course:build` performs offline compilation without a model, network or database. The review packet includes unresolved regional/register review findings. The SQL output ends with `ROLLBACK` and is not a publication script to run blindly.

For another subject, write a new blueprint, use appropriate existing or reviewed draft KCs, supply course metadata, and author its own scenarios. Reuse the contract and checks, not the financial examples. Hundreds of lessons require distinct outcomes and evidence; adding names or numbers to a copied lesson is explicitly rejected.

## Release and measurement

The review tool also offers "Review from" to enter an individual authored step. Earlier steps are treated as viewed/met only in that local preview; this is navigation for authors, never an authenticated completion or a learner mastery record. Use the first step when inspecting a complete teaching sequence. The compiler emits lessons in blueprint order even when filenames sort differently.

From `frontend/`, verify the actual compiled content with `npm run verify:lesson-engine -- --course-documents ../coursegen/runs/solid-course/documents.json --mobile --light`; omit `--mobile` for desktop and `--light` for dark theme. `--only <segment-type>` is an explicitly filtered diagnostic, not a complete-course pass. This mode starts a separate loopback review server on port 5198, validates the corpus through Core, and examines each authored step in the real player. It checks copy budget, text fit, proportions, control reachability, help, media and JavaScript errors. Reports under `audit-results/lesson-engine-authored/` include the source hash and expected/measured counts. Each step is entered through author-preview navigation; it does not prove complete graded journeys, keyboard accessibility, authenticated progress or learner comprehension. Source changes invalidate the corresponding report.

For a repair pass, `--cases <file>` accepts a nonempty JSON array of `{ "lesson": "authored-id", "locale": "en-US", "segment": "step-id" }`. Unknown and duplicate cases are rejected before browser startup; `--cases` cannot be combined with `--only`. Reports remain explicitly filtered. Include every failed or changed screen and every screen affected by a shared layout change. Preserve the prior report and its exact input snapshot; a filtered pass alone never certifies the entire updated course.

Add `--choice-interactions` to exercise authored `story.branch.v2` screens through real pointer controls and the local Core grader. The driver submits each incorrect choice, checks the exact authored feedback (choice-specific when present, otherwise the authored error explanation), corrects the answer, and verifies advancement to the next authored step. It rejects cases from unsupported board types and writes a separate `*-choice-interactions` report. Private answer keys stay in the local test process and grading server; they are not inserted into the public lesson document. This proves only the named choice interactions: it does not certify simulator interactions, authenticated persistence, uninterrupted whole-lesson journeys, or learning outcomes.

Use `--board-interactions` separately for server-graded running ledgers, percent grids, unit-price comparisons and charts. The driver enters numbers using real keyboard input, manipulates sliders through keyboard events, submits an incorrect result, verifies authored feedback, corrects the result and advances. It writes a separate `*-board-interactions` report and rejects unsupported cases. This mode excludes ungraded exploration boards and does not prove authenticated persistence. Run browser modes sequentially, preserving each input snapshot and report; an implemented driver is not passing evidence until its measured report succeeds.

Explicit arithmetic equalities in Mentor teaching lines and recovery statements are recomputed. Deliberately wrong candidate answers and the Mentor's staged mistake are excluded. This supplements the private numeric-choice proofs and board-specific arithmetic checks; prose claims without a supported equality still need semantic review.

Live `v2:publish` requires the whole-course blueprint, complete plan set and `--lesson-ids` mapping before network access. Its course verification uses those exact files, never a historical catalog selected only by course name. Existing release, regional, pedagogy and repository gates still apply. The compiler does not approve release or replace the operator runbook in `FORGE-V2-RELEASE.md`.

For a separate Vault-backed verification, use `npm run verify:course -- <course> --blueprint <file> --plans <directory> --lesson-ids <file>` from `coursegen/`. All three source arguments are required together; malformed, missing or aliased mappings are rejected. This command can write a release attestation when every check passes, so it belongs to the reviewed release procedure, not offline authoring.

Deploy Core support for personal ledgers and per-choice hints before a frontend or lesson payload that uses those strict wire fields. Live publication refuses them without `--core-has-instructional-fields`, which confirms deployment, not teaching quality. Seed and review the new KC graph before making lessons reachable. Preserve immutable lesson versions and learner records. An archived course is withdrawn, not physically deleted. Restore/archive decisions and production mutations follow the explicit task authorization and backup procedure.

After release, compare independent first-attempt transfer and later retrieval, not just retries until correct. Track abandonment by segment and board, subsequent learning sessions and return rates with the existing consent and age rules. Repeated failure should lead to a prerequisite explanation and fresh practice, not merely replaying the same key. Real improvement requires learner evidence; do not replace it with a model-generated quality score.
