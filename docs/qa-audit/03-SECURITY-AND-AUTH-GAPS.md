# Security and Auth Gaps

**Scope & method.** Static review of routing middleware and every route handler in `backend/` (Core, the only service the SPA calls directly) and in the eight internal-only services that Core and each other call over Railway private networking: `oracle/`, `coursegen/`, `audiogen/`, `picturegen/`, `dataintel/`, `email-server/`, `filebase/`, `parent-id-check/`. For each route, three questions were asked: is it authenticated at all; if authenticated, is the caller verified as authorized for the *specific* resource in the request (not just "any logged-in user") — the confused-deputy/IDOR pattern; and is the input validated before use. Findings were spot-verified directly (not solely trusted from automated read-out) against `backend/src/app.ts`, `backend/src/middleware/auth.ts`, and several route files.

**Overall posture.** This is a defensively-built codebase, not a green-field one. `requireAuth` is applied per-router (not globally in `app.ts`) but every router that isn't one of three explicitly-commented public exceptions applies it. Parent/kid-scoped resources are re-verified against `guardian_links` on essentially every request via shared guard functions (`guardKid`, `guardParentOf`, `isVerifiedGuardian`) rather than trusting a URL parameter. Zod `.strict()` schemas gate nearly every request body. The internal-service boundary (`x-internal-api-key`, timing-safe compare) is applied consistently at the app-mount level across all eight internal services. No unauthenticated route reachable from the public internet was found beyond the ones the code itself documents as intentionally public. The findings below are the gaps that survived that baseline — mostly consistency and scoping issues rather than open doors.

---

## Unprotected Routes

No route was found in `backend/` or in the eight internal services that lacks authentication and was not one of the following, explicitly-documented-as-public exceptions:

- `backend/src/routes/badgePublic.ts:25` — `GET /api/v1/badges/:token`, an opaque per-badge token lookup with no session, by design (`app.ts:65-68`).
- `backend/src/routes/analytics.ts:34` — `GET /api/v1/analytics/tracking-decision`, a per-caller-IP boolean with no account data.
- `backend/src/routes/events.ts:153-216` — the anonymous branch of the events beacon, restricted to a fixed allowlist of acquisition-only event types and route classes (`ANON_EVENTS`/`ANON_ROUTE_CLASSES`, `events.ts:48-69`).
- `oracle`'s `/ws/tutor` websocket (`oracle/src/ws/server.ts:1488`), gated by single-use signed session tokens (`oracle/src/session/token.ts:131`) instead of the internal-key header — the one documented exception in the service map.
- `filebase/src/routes/download.ts:102-108` — public-visibility file reads are unauthenticated by design ("Depot reads" are the one public surface of that service per the README); the same handler still requires the internal key for any object marked `internal` visibility, and writes (`filebase/src/routes/files.ts`, `badges.ts`) are gated by `requireInternalKey` at `filebase/src/app.ts:30,32`.

One service-level note, not a live vulnerability: **`coursegen/`** has no internal-key middleware anywhere in the service (`coursegen/src/app.ts` only defines `GET /health` and a 404 catch-all). This is not currently exploitable because the service has no other HTTP routes to protect — its pipeline code is invoked out-of-band, not over Express — but it means the internal-key pattern every other service applies at the app-mount level is absent here, so a route added to `coursegen/src/app.ts` in the future would be unauthenticated by default unless someone remembers to add the gate that exists everywhere else.

## Data Exposure

1. **`dataintel/src/routes/queries.ts:554,566,603`** — `GET /learning/states/:userId`, `GET /learning/recommendation/:userId`, and `GET /learning/learners/:userId` return per-learner skill-state and recommendation data keyed by a raw `userId` path parameter, with no additional scoping check inside the handler beyond the shared internal-key gate applied at the app level (`dataintel/src/app.ts:41-56`). Because `INTERNAL_API_KEY` is one secret shared across all eight internal services (per the README's stated model), any service holding that key — not only Core, which is the caller with legitimate business need — can pull any child's learning profile by UUID with no per-caller or per-role scoping.

2. **`email-server/src/app.ts:60-74,113`** — `GET /api/v1/logs` returns full email log rows, including recipient (`to`) addresses and `userId`, with pagination but no field redaction. The endpoint is internal-only, which lowers severity, but it is unfiltered PII returned in bulk to any caller holding the shared internal key. Separately, this route's internal-key check reads `process.env.INTERNAL_API_KEY` directly (`email-server/src/app.ts:62`) rather than through the config module every other service uses — an inconsistency, not itself a vulnerability, since the comparison still fails closed when the variable is unset (line 70).

3. **`backend/src/routes/admin.ts:1231-1637`** — email logs, insights, and intel-export/proxy routes rely solely on the router-level `requireRole(['admin','superadmin'])` gate (`admin.ts:372`) with no additional per-route permission check, even though this same file implements a finer-grained `ADMIN_PERMISSIONS` system (`admin.ts:105-114`, used to gate role/permission mutation at lines 1178-1229). That finer-grained system is never consulted for any *read* route — every admin and superadmin can read every analytics/email/intel surface. The file's own comments describe the permission system as covering "anything beyond reads," so this may be the intended scope rather than an oversight, but it means there is currently no way to grant an admin narrower read access than the full analytics/email/intel surface.

No `select=*` or other full-row pass-through to a client-facing response was found anywhere in `backend/src/services/supabaseRest.ts` — every sampled query (profiles, tasks, banking accounts, redemptions, wallet ledger, badges, course hierarchy) enumerates specific output columns. `backend/src/routes/badgePublic.ts:32-37` and `backend/src/routes/profile.ts:113-121` (`publicShape`) both explicitly narrow their public-facing responses (excluding `kid_user_id`/`created_by`/row `id` from the badge share, and `birth_date` from public profile views) even though the underlying service functions fetch the full row.

`parent-id-check`'s verification response (`parent-id-check/src/services/matching.ts:20-24`) is a minimized boolean verdict (`verified`, plus four boolean sub-checks); raw OCR text and the uploaded identity document are never returned, logged, or persisted to disk (`parent-id-check/src/routes/verifications.ts:54-59` deliberately swallows error detail to avoid echoing document content; the image buffer is memory-only via `multer.memoryStorage()`).

## Input Vulnerabilities

1. **`backend/src/routes/family.ts:395`** — `GET /kids/:kidId/courses/:slug/territory` reads `req.params.kidId` with a plain `as string` cast, skipping the `z.string().uuid().safeParse` validation every sibling route in this file applies (e.g. `family.ts:268-271`). This is not currently exploitable — the subsequent guardian-link membership check still gates access, so a malformed id simply fails to match any link and 403s — but it is the one route in this file that doesn't follow its own stated pattern ("every kid read re-verifies... before any service-role fetch").

2. **`backend/src/routes/verification.ts:26-31`** — computes a parent's age using an averaged-year formula (`(Date.now() - Date.parse(d)) / (365.25 * 24 * 3600 * 1000)`). This is the same bug class that `backend/src/routes/auth.ts:48-86` (`yearsOld`) was already rewritten to fix with a calendar-based calculation, per that function's own comment. The drift in `verification.ts` is conservative (it can only compute an age slightly *younger* than actual near a birthday), so it produces a false-rejection UX bug rather than an age-gate bypass — but it is a live inconsistency between two age checks in the same codebase, one fixed and one not.

3. **New idempotency-cache trust boundary in uncommitted changes** — `backend/src/services/supabaseRest.ts:661-681` together with `database/migrations/0084_atomic_segment_grading.sql:8,44` changed how the `attempt_number` field (wired through as `p_client_attempt`) is used. It is now part of the primary key of an idempotency-receipt cache (`lesson_grade_receipts`, keyed on `(user_id, lesson_id, run_id, segment_id, client_attempt)`), and the SQL function (`0084...sql:41-46`) returns the *cached* prior verdict on a repeated `client_attempt` value without re-grading the newly submitted answer. The real attempt cap is still enforced independently from a `count(*)` over `lesson_segment_attempts` (`0084...sql:47-50`), so this cannot be used to exceed the attempt limit — but it is a new trust boundary that did not exist before this change (the prior `learn.ts` computed `serverAttemptNumber` from a real DB count and ignored the client-supplied value entirely). A client that fails to monotonically increment `attempt_number` for a genuinely new submission within a `run_id` will silently receive the stale prior grade instead of a fresh one, with no error surfaced to distinguish the two cases.

4. Free-text fields carry explicit length caps throughout: task titles (`backend/src/routes/tasks.ts:208`, 120 chars), profile display names (`backend/src/routes/profile.ts:70`, 80 chars), placement intake text (`backend/src/routes/placement.ts:104`, 4000 chars, plus a fail-closed moderation check), tutor turn text (`backend/src/routes/tutor.ts:1104`, 4000 chars), notebook/whiteboard labels (40-60 chars). In the internal services, `audiogen`'s narration text (`audiogen/src/routes/audio.ts:14-18`, 4000 chars) and `picturegen`'s prompt fields (`picturegen/src/routes/pictures.ts:7-19`, label 300 / context 2000 chars) are both zod-bounded before reaching generation. No unbounded free-text field reaching storage or a model prompt was found.

5. No path-traversal exposure was found in either file-handling service: `filebase`'s bucket/hash/extension parameters are all whitelisted by regex (`filebase/src/lib/validation.ts:8-10`) before any `path.join`-based filesystem access, and `picturegen` does not build filesystem paths from user-supplied label/context text.
