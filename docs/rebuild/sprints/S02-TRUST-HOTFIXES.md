## S02.2c transactional freeze enforcement

Migration 0093 introduces a shared row-lock check against `banking_accounts`. Existing task allocation, pending-credit allocation and scheduled-credit functions acquire their existing wallet advisory lock, then lock the banking account before moving value. A freeze updates that same row, so it cannot acknowledge in the middle of an already admitted movement. Frozen allocation returns without changing the earned/pending record; frozen scheduled processing returns without advancing dates. New redemption inserts are guarded by a trigger; approvals of existing requests are held while frozen, while denial remains available.

Browser roles lose table-wide banking-account UPDATE permission and receive only nickname/card-design UPDATE. Freeze and attribution changes therefore go through Core's authorized routes, including the ownership guard from S02.2a. Service function execution remains restricted. The migration preserves the existing goal-tagging, allocation validation, credit cap, ledger semantics and missing-account family-wallet compatibility.

`database/scripts/verify-freeze-postgres.py` applies the actual 0093 functions to fresh minimal native PostgreSQL fixtures. It verifies task/allowance holds, unchanged schedule dates, rejected redemption requests, denied direct-browser unfreeze, resumed processing without lost credits and replay without ledger changes. It also observes actual lock waits in both orders: freeze first holds a waiting allocation; allocation first completes before freeze acknowledges. Existing redemption approval is held while frozen; denial still succeeds. Evidence: `audit-results/s02-freeze-postgres.json`. These are real transaction tests, not mocked lock outcomes, but they do not replace the full Supabase/RLS stack.
