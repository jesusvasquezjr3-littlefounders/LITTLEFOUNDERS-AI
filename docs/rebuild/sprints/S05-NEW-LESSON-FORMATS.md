# S05 authoring contract for future lesson formats

This is an implementation runbook for the future engine and Forge phases, **not** a new source of product requirements. The binding rules are [OD-16/17](../../littlefounders-spec/product/13-OWNER-DECISION-LOG.md), Product B.6–B.8 and Appendices A/C/P, and Frontend Bible 02/05–08. The current frontend pilots do not yet satisfy this runbook end to end.

## Invariants for a format addition

1. Start with a named knowledge component, misconception and learning objective within one thematic course. Author the age-appropriate pathway and prerequisites separately from the learner's age safeguard. Do not clone a course merely to add an adult register or require adults to pass childhood chapters.
2. Assign stable course, pathway, chapter, lesson, version, locale and segment identifiers. Published versions are immutable; a correction creates a new version and preserves active work and old evidence. The local S05.2 storage supports immutable version rows, a current pointer, version-pinned runs, nonces and grade receipts. It does **not** yet supply reviewed publication, completion aggregation, active-run recovery or a catalog migration.
3. Put only presentation data, a bounded eligibility policy and permitted manipulable parameters in the client document. Answer keys, hidden tests, rubric weights, scoring thresholds, protected age evidence and authority to award progress stay on the server. Core turns protected date evidence into only an allow/deny decision before a v2 document is delivered, graded or completed; the client must never derive or receive a date or numeric age. Strictly validate the segment schema and reject unknown fields, versions and capabilities. The supported client types and their capability declarations currently live in `frontend/src/rebuild/learning/lessonDocument.ts`; a new type must be added to its exhaustive capability map and both exhaustive support/render switches in `LessonDocumentView.tsx` together. The current `money.allocation.v2` visual variant must declare exactly its renderer capability (`visual.stacked-bar.v1`, `visual.waffle.v1` or `visual.donut.v1`) plus the shared reallocation capability; the waffle pilot is restricted to ten one-coin rows for ages 6–9 and the donut pilot to sixty coins in five-coin steps for ages 10–12. M7 is an exact-10–12 ordered pair: `math.bar-model.structure.v2` must precede `math.bar-model.answer.v2`, with two separate rubrics, tokens and receipts; the answer token is not consumed unless Core records a met structure receipt. The controlled `math.ratio-table.v2` pilot is restricted to the 10–12 three-items-for-fifteen-coins scenario and declares its ratio-table, parameter-slider and linked-representation capabilities; it supplies two linked direct-drag handles with the native control as the accessibility alternative. The controlled M20 `visual.tax-bracket.v2` candidate is restricted to the exact 14–17 eligible subset within the `13-17` pathway; it declares only progressive stacked-bar, parameter-slider and linked-representations capabilities, and its browser arithmetic is generated from the Core minor-unit source. The controlled M13 `math.function-machine.v2` pilot is exact-10–12: it declares function-machine, try-input, guess-rule and held-out-check only. Public linear examples are teaching material; private held-out inputs must be unique and distinct from every public input. Declare only the interaction actually implemented: the current savings-rule pilot offers `operation.choose-connective.v1`, not a general `operation.build-rule.v1`. Place-value and running-ledger pilots now declare `operation.step-replay.v1`. The controlled M9/M10 candidate separately declares worked-example, replay, prediction, backward-fade and number-input capabilities. Its exact post-initial step-value set is now server-scored through the canonical scorer and signed-attempt boundary; mastery-driven fade selection remains open.
4. Design the visible activity from the SPEC before generating content: neutral Pizarrón representation, HTML controls and labels, tap and keyboard alternatives for drag, table for every chart, semantically named state, task-scoped feedback and first-view action. Use the shared board shell and `ParameterSlider` for bounded live parameters, platform-neutral tokens, `data-copy-role` and only reviewed in-house assets. A new visual family must be entered in [the coverage ledger](S05-VISUAL-COVERAGE.md), with its owner-review states in [the visual register](S05-VISUAL-REVIEW.md).
5. Define one canonical semantic response shape and a pure scorer callable by Core and the client for prediction and preview parity. For the first two graded pilots, edit only `backend/src/services/v2VisualScorer.ts`, regenerate the byte-identical browser copy with `node agent/tools/sync-v2-visual-scorer.mjs`, then pass its `--check` gate. Core alone issues and consumes a signed, single-use, version-pinned attempt token and validates impossible states. The current runtime persists canonical verdicts and completes supported immutable scored formats with server-owned XP. A new format must still prove its own scoring, retry, completion and physical-database evidence before it claims progress authority. The development preview's fixture rubrics and local checkpoint are not this boundary.
6. Author per-locale `spokenText`, number/currency conventions, concise prompts/options and age-register variants. Test the entire allowed input range where the activity is gradable, including off-grid, replay, expired token, stale version, reload, wrong answer/revision and concurrent grade attempts. A happy-path fixture is insufficient.
7. Produce the lesson through Appendix C's human and automated stages: human competency scope, bounded generation, deterministic checks, named pedagogical review, target-age usability pilot for a new format, versioned publication and monitored recalibration. Forge and bulk course regeneration begin only after the integrated engine and owner-reviewed screens pass S05's exit gate.

## Current local implementation boundary

### M1 engine rule: required contract before catalog authoring

M1 is not a visual widget and must not be represented as one. A governed item needs an immutable `fading_group_id`, an ordered `concrete`, `pictorial`, `abstract` representation stage, a common semantic problem identity and its authored support level. The learner sees the same problem through those linked representations; later items remove earlier representations and a learner already fluent at a later stage must not be returned to concrete. The final symbolic response remains the only M1 completion-required server-scored semantic response; earlier stages are attempted representations and diagnostics. The first successful stage is a diagnostic record created by Core from an authenticated, version-pinned successful stage receipt. It is never a browser-declared field, an XP input or a reason to change an in-flight attempt; it cannot be described as fully unaided until the Mentor owns support/hint attribution.

Migration 0105 stages an idempotent Core-only per-group first-success diagnostic tied to one met immutable receipt; migration 0106 adds the ordered attempted-receipt guard for its three-stage M1 sequence. The guard intentionally permits progression after a review, but it does not determine whether Mentor support was supplied. Immutable-version recovery behavior, Mentor-support ownership and adaptive entry policy remain required before a first M1-governed item is accepted. The existing M5, M9/M10 and M13 candidates demonstrate representations that can later be governed by this rule, but none may claim M1 acceptance or emit an "unaided" metric today. This is an explicit engine blocker for Forge/catalog generation rather than a reason to put an untrusted `unaided` flag in generated lesson content.

Twenty-one controlled v2 pilot segment types and twenty visual variants are implemented in the isolated preview: allocation (stacked bar, waffle or donut), savings line, bounded whole-number line, bounded fraction/decimal line, equal-area fractions, an M7 comparison bar-model pair, an M8 change-schema trio, an M9/M10 worked-example candidate, an M13 function-machine candidate, savings-goal bullet chart, linked percent grid, base-ten exchange, a conditional savings-rule diagram, a signed running ledger, a simple/compound growth comparison, a tween ratio-table/unit-price candidate and a 14–17 M20 marginal-tax candidate. M1 now has a controlled engine slice: one immutable group binds concrete, pictorial and abstract segments with identical addends and strictly declining authored support. Core rejects a direct later-stage request until it has a same-run receipt for the prior stage, while allowing that receipt to be a review. Core records the first met stage from immutable metadata and a signed receipt, but Mentor support attribution and physical-database proof remain open. M3 is an exact-10–12 fraction/decimal candidate: it keeps its target and tolerance private while linking an equal-area strip to the number line and accepts only grid-valid semantic fractions; a controlled immutable run verifies review, equivalent-fraction met and version-pinned completion. M6 is an exact-7–9 area candidate: it permits only bounded equal partitions, keeps the target private and compares semantic fractions by cross multiplication; a controlled immutable run verifies review, equivalent-fraction met and version-pinned completion. M7 is an exact-10–12 two-step candidate: comparison structure is scored before an independent bounded arithmetic response can be submitted. M8 is an exact-10–12 three-step candidate: the learner selects a change schema, fills the two visible values and then submits the remaining amount; Core requires the preceding met receipt before each next token can be consumed. M13 is an exact-10–12 function-machine candidate: public bounded linear examples feed a required trial, while a private rule and distinct held-out inputs score the submitted `{ multiplier, offset }` pair. The M15 percent candidate is restricted to the 10–12 pathway and matching policy, a safe subset of its 10–14 Appendix P range; other preview bands are refused. The M20 candidate is a safe exact-14–17 subset within the teen pathway; its progressive SVG bar, native income slider, table and summaries use one generated canonical pure Core/browser model but it remains unscored. The ratio-table candidate supplies linked direct-drag handles with bounded slider/stepper alternatives. The base-ten and ledger pilots share one controlled step-replay component. A distinct exact-10–12 M9/M10 worked-example candidate now provides authored step rows, free scrub replay, prediction-required reveal and bounded backward fading to native fields. It has a canonical server score and uses the existing signed-attempt/retry/completion path when delivered through the authenticated route; adaptive fade selection and all publication/acceptance evidence remain open. A two-activity preview, normal/replay sample results, two refusal states and three lesson transport-state presentations demonstrate navigation and visual hierarchy without server-saved progress. The transport states cover opening, offline and load-error presentation only; their Retry in the preview switches to a fixture, not a real network request. The normal document view refuses unsupported multi-segment publication except the exact M1, M7 and M8 sequences. Every v2 document requires a bounded eligibility policy and Core fail-closes delivery, grade and completion from protected profile evidence. Allocation, whole-number-line, fraction-number-line, fraction-area, both M7 segment types, all three M8 segment types, M1 and M13 share one canonical pure scorer source with a generated browser copy; growth comparison and M20 each have a separate generated canonical pure Core model, but neither is scored. The local engine now has immutable v2 rows, activated-pointer selection, a short-lived signed run/token, nonce-bound canonical grade receipt and an authenticated Pizarrón bridge for twelve scored segment types. It has version-pinned v2 completion/XP aggregation for supported scored segments and persisted reload recovery, but no reviewed publication workflow, complete Appendix A/P library or accepted real-app player. The build gate intentionally refuses seven draft visual assets. These missing pieces are required before this runbook can be used to generate a new lesson catalog.

Core also performs a strict public/private preflight before serving a v2 document: it validates the complete answerless public shape, selected lesson and locale, controlled visual restrictions, and one private rubric for each of the eleven canonical scored segment types only. This is a delivery-integrity check and does not replace the remaining reviewed publication, completion and acceptance requirements.
