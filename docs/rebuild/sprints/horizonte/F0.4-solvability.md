## What it proves, and where it runs

Before Forge publishes a generated instance of an interactive board it must prove, by machine, that the instance is a correct, solvable and meaningful puzzle:

1. A solution exists.
2. The solution is unique, or every valid solution is covered by the private rubric.
3. Nothing overlaps (grid cells, rectangles, points, intervals).
4. The learner cannot reach an impossible state (a dangling reference, a total above capacity, a dead end).
5. The rubric neither rejects a valid answer nor accepts an invalid one.

It runs inside `runV2DocumentGates`, which the emitter calls once per market with the answer keys, and which `release/evaluate.ts` calls on stored public documents with no answer keys. The verifier is deterministic and offline: no clock, no randomness, no network, no model call. Every search runs under a node budget (counted work, not time), so an instance can never hang the pipeline.

Core stays the grading authority (`v2VisualScorer.ts`, `v2LessonDocument.ts`). Packages share no code by design, so Forge pre-checks the same facts cheaply and Core remains the strict judge.

## Gate number: findings ride gate 1

A dedicated gate number needs a database migration (rows in `forge_release_gates` and `forge_v2_manifest_gates`), `gateManifest.ts`, `V2_MANIFEST_GATES` in `v2/release.ts`, `gateSubmissionLog.ts`, the parity script and a production re-attestation. That is a production change the owner decides, so solvability findings use gate 1 (structure) for now:

- A blocking finding is a `GateProblem` with `gate: 1`, the segment id, and a message that starts with `solvability/<code>: `.
- A review finding goes to the Stage 3 reviewer under the same gate and prefix.
- The number is one constant, `SOLVABILITY_GATE` in `gates.ts`. Reports and metrics can filter on the `solvability/` prefix.

To promote it to its own gate 20 later: widen `GateNumber` (`pipeline/gates.ts`), add the migration rows for both tables, add the `gateManifest.ts` entry and the `V2_MANIFEST_GATES` entry, add 20 to `ALL_GATES` in `gateSubmissionLog.ts`, run `forge:release-gates:check`, re-attest live courses, then change the constant. The test `v2Emit.test.ts` hard-codes the red-team gate list, so a gate 20 red-team sample goes into that list in the same change.

## API

Everything is exported from `coursegen/src/v2/solvability.ts`. The file has no runtime imports (a test enforces it), so any pack can import it without a cycle.

### Registry

```ts
registerSolvabilityChecker(type: string, checker: SolvabilityChecker): void   // throws on a second registration of a type
unregisterSolvabilityChecker(type): boolean                                    // test seam
solvabilityCheckerFor(type): SolvabilityChecker | undefined
registeredSolvabilityTypes(): string[]
solvabilityCoverage(types): { checked: string[]; unchecked: string[] }

type SolvabilityChecker = (segment: SolvabilitySegment, context: SolvabilityContext) => SolvabilityResult
interface SolvabilitySegment { id: string; type: string; grading?: string; payload: Record<string, unknown> }
interface SolvabilityContext { answerKey: unknown; ageBand?: string; locale?: string; nodeBudget: number }
interface SolvabilityResult { ok: boolean; issues: SolvabilityIssue[]; stats?: Record<string, number> }
interface SolvabilityIssue { code: SolvabilityCode; severity: 'block' | 'review'; message: string; path?: string }
```

A segment type with no registered checker passes unchanged. `answerKey` is the segment's private rubric when the caller has it (the emitter does; release-time verification of a stored public document does not, so it is `undefined` there). A checker proves what the public payload alone determines, and the rubric-dependent half only when `answerKey` is defined.

Build results with `issue(code, message, { severity?, path? })`, `result(issues, stats?)` and `mergeResults(...)`. Codes: `no-solution`, `ambiguous-solution`, `rubric-gap`, `rubric-accepts-invalid`, `overlap`, `out-of-bounds`, `impossible-state`, `dangling-reference`, `duplicate-id`, `dead-end`, `vacuous-rubric`, `too-large`, `budget-exceeded`, `checker-error`.

### Budget

`Budget` is a hard work cap: `budget.spend(units)` returns false once the cap is passed and the caller must stop and report `budgetIssue(...)`. `clampBudget` keeps any request inside `DEFAULT_NODE_BUDGET` (200,000) and `MAX_NODE_BUDGET` (2,000,000). `context.nodeBudget` is the per-segment cap; pass it to every search and every loop that grows with the instance.

### Search helpers

| Helper | Use |
|---|---|
| `searchAssignments({ domains, distinct?, accept?, isSolution?, key?, limit?, maxNodes? })` | Backtracking over one domain per slot (a count per denomination, a value per cell, a choice per rule). `accept` prunes partial assignments. |
| `searchArrangements({ pool, slots?, kind?, accept?, isSolution?, key?, limit?, maxNodes? })` | Ordered arrangements of a pool of items into slots (tiles into an equation, cards into an order). Items of one `kind` are interchangeable, so swapping identical tiles is not a second solution. |
| `exploreStateSpace({ initial, moves, isGoal, key, full?, maxDepth?, maxNodes? })` | Bounded breadth-first search: goal reachable, shortest solution, count of shortest solutions, and with `full` the reachable dead ends. `complete` is true only when the whole reachable space was explored, which is what makes "goal not reached" a proof. |

Both searches return `{ solutions, keys, count, exhaustive, stoppedAtLimit, budgetExceeded, nodes }`. Two solutions with the same `key` are one solution, so the key is where a pack states what "the same answer" means (for example operand order in a commutative equation). The default `limit` is 2, enough to prove or refute uniqueness.

### Uniqueness, coverage and reachability verdicts

- `verifyUniqueOrCovered(run, { subject, acceptance?, isSolution?, predicateGraded? })` applies the F0.4 rule over an enumeration. `run(limit)` performs the search; the verifier picks the limit (2 for uniqueness, `COVERAGE_LIMIT + 1` = 501 for coverage).
  - No solution blocks (`no-solution`). A budget overrun blocks (`budget-exceeded`).
  - With `acceptance` (a set or list of canonical solution keys, or a predicate), every valid solution must be accepted (`rubric-gap`), and an explicit list may not accept a non-solution when `isSolution` is given (`rubric-accepts-invalid`). More than 500 solutions cannot be shown covered and block; grade such a board by predicate.
  - With `predicateGraded: true` the server scorer grades by the predicate that defines a solution, so only existence matters. Say so explicitly; the default demands a unique solution or an explicit rubric.
- `checkRubricCoverage(solutionKeys, acceptance, { subject, isSolution? })` is the coverage half on its own.
- `judgeReachability(explored, { subject, requireUniqueShortest?, forbidDeadEnds? })` turns an `exploreStateSpace` result into a verdict: unreachable goal, several shortest solutions, a dead end the learner can wander into, or an exploration that did not finish.

### Overlap and impossible-state predicates

| Helper | Checks |
|---|---|
| `checkGridPlacement(cells, grid?, { maxNodes? })` | Whole positive positions and spans, inside the grid, no two cells sharing a square. Budgeted. |
| `checkRectLayout(rects, { gap?, bounds? })` | Finite positive sizes, inside the bounds, none overlapping or closer than `gap`. Touching is allowed at gap 0. |
| `checkPointSpacing(points, { minDistance, bounds? })` | Finite positions, inside the bounds, none closer than `minDistance`. |
| `checkIntervalOverlap(intervals, { allowTouching? })` | Well-formed intervals (finite, start at or before end), none overlapping. |
| `checkUniqueIds(ids, label?)` | No repeated id. |
| `checkReferences(refs, knownIds)` | Every reference points at an element that exists. |
| `checkInvariants(subject, [{ check }])` | Any impossible-state predicate: return a message when violated. |

The pairwise layout helpers refuse more than `MAX_LAYOUT_ELEMENTS` (2,000) elements with `too-large`, and list at most five problems plus a count, so a badly broken board stays readable.

### The runner

`runSolvabilityGate(document, answerKeys?, { nodeBudget? })` returns `SolvabilityFinding[]` (`severity`, `segmentId`, `type`, `code`, prefixed `message`). `gates.ts` maps them to gate-1 problems and review items. It fails closed: a checker that throws, returns a malformed result, reports `ok: false` without naming a blocking issue, or uses an unknown severity all block. A result whose issues contain a blocking issue blocks even if the checker said `ok: true`; the issues are the source of truth.

## How a pack registers its checker

1. Write the checker in the pack's own module, `coursegen/src/v2/horizonte/<pack>.ts`. Import only from `../solvability.js` (and, if needed, `../contract.js`). Never import `../gates.js`, `../emit.js`, `../cli.js` or `../solvabilityPacks.js`: `gates.ts` loads the pack through `solvabilityPacks.ts`, so those imports would form a cycle. A test fails if a horizonte module does.
2. Register at module top level, one checker per segment type:

   ```ts
   import { registerSolvabilityChecker, searchArrangements, verifyUniqueOrCovered, type SolvabilityChecker } from '../solvability.js';

   const tileEquation: SolvabilityChecker = (segment, context) => {
     const tiles = segment.payload.tiles as string[];
     const holds = (full: readonly string[]): boolean => isTrueEquation(full);
     return verifyUniqueOrCovered(
       (limit) => searchArrangements({ pool: tiles, isSolution: holds, limit, maxNodes: context.nodeBudget }),
       { subject: `tile equation ${segment.id}`, ...(context.answerKey !== undefined ? { acceptance: acceptedKeysFrom(context.answerKey) } : {}) },
     );
   };

   registerSolvabilityChecker('horizonte.tile-equation.v2', tileEquation);
   ```

3. Add one line to `coursegen/src/v2/solvabilityPacks.ts`: `import './horizonte/<pack>.js';`. That file is the only list `gates.ts` loads. A test fails when a horizonte module calls `registerSolvabilityChecker(` and is not listed there, so a registered proof cannot silently go unloaded.
4. The segment type must be a real `V2_SEGMENT_TYPES` entry (a test checks every registered type).
5. Add tests next to the pack: a solvable instance, an unsolvable one, an ambiguous one (or one the rubric covers), and one that exhausts a small `nodeBudget`.

Rules every checker follows:

- Validate the payload shape defensively and return an `impossible-state` issue for a malformed payload; do not assume Core's parser ran.
- Spend `context.nodeBudget` in every loop that grows with the instance. When the budget runs out, return `budgetIssue(...)`: "could not prove it" is never "it is fine".
- Prove existence and uniqueness (or rubric coverage) from the public payload when `answerKey` is `undefined`; add the rubric-dependent proofs only when it is defined.
- Use `severity: 'review'` only for advisory findings (a board that tests nothing); anything that makes the learner unable to succeed or to be graded fairly is `block`.

## Shipped checkers

`solvabilityBuiltins.ts` registers the two money boards, both of which Core grades by total, so existence is what matters:

- `money.coin-tray.v2`: the tray is well formed (2 to 8 strictly descending denominations); with the rubric `{ target_minor, fewest }` the target is whole, positive, at most 100,000 and at most the tray's total, and some mix of the available pieces makes it exactly (bounded knapsack with a sliding-window minimum, linear in the target per denomination). With `fewest: true`, a board where every way to make the target uses the same number of pieces gets a review finding (`vacuous-rubric`).
- `money.making-change.v2`: price and payment are whole with payment above price; the change owed (payment minus price) is formable from the tray's available pieces, and needs at most 60 pieces (Core's counting-up sequence limit); with the rubric, `change_minor` equals payment minus price. Formability is proved from the public payload, so it also runs at release time on stored documents.

The shipped lesson plans were unaffected. The red-team sample `gate03-currency-facts.json` (a making-change board with a coin no market issues) was also genuinely unsolvable (700 owed, at most 590 reachable without the 1000 bills), so the new gate correctly flagged it on gate 1 as well and broke that file's "blocks on exactly its own gate" test. Its 100-coin count went from 5 to 7 so the board is solvable and the sample again blocks on gate 3 only.

## Limits

- The budget is counted work. A coin-tray or change target above about 25,000 minor units with 8 denominations exceeds the default budget and blocks with `budget-exceeded`; raise the budget deliberately or write a smarter checker.
- Review-severity findings go to the Stage 3 reviewer; they never block.
- The verifier proves the facts a checker states. A wrong checker is a wrong proof, so every pack checker needs its own tests, including an unsolvable and an ambiguous instance.
- Release-time verification of stored documents has no rubric, so the rubric-dependent proofs (coin-tray target reachability, rubric coverage) run only at emit time, where Forge has the plan.
- Core also scores permitted states of each emitted segment (`forge-v2:check`, the interactive-behaviour gate). That is complementary: Core checks that the contract grades every reachable response, this module checks that a solution exists and that the instance is meaningful.
