## Owner-confirmed outcome and boundaries

- A subject is one thematic course with age-appropriate chapters and lessons for children, adolescents and adults. Placement and shared mastery choose an eligible frontier; adult learners do not have to complete childhood chapters, and minors do not need adult chapters for their eligible completion.
- Deliver the optimized learner-facing lesson UI, chart renderer and interactive Pizarrón first, using controlled fixtures and a minimal contract. Then complete the document contract, authoritative grading, recovery and compact Mentor presence around the proven experience. The frontend is new under the Bible, with no legacy UI component imports. The backend is migrated, not rewritten wholesale (OD-2).
- Adapt Forge and regenerate the catalog only after the new contract and a complete pilot lesson pass product and frontend gates. A possible total near 400 is illustrative, not an acceptance target. Curriculum coverage, age fit and review determine the final count.
- Existing DeepSeek/Qwen settings remain unchanged during engine design. Provider roles and costs are reassessed in the later Forge phase. No bulk paid generation is authorized by this checkpoint.
- No existing lesson or learner evidence is deleted to simplify migration. OD-9 requires preserving progress, placement credits, XP, badges, streaks and Mentor artifacts. No production mutation or deployment is authorized during this migration.

## Phase A: experience-first engine and a complete authored pilot

1. **Visible interface and interaction foundation.** Start from Frontend Bible 02/03/05–08 and the new design-system controls. Build a reusable lesson shell, question/answer layout, chart/board renderer, interaction controls and loading/error/recovery states against controlled fixtures. Verify visual composition, text fit, copy budget, touch targets, accessibility, motion, low-power behavior and performance on narrow and wide devices in all three locales and both themes. This is a real frontend foundation, not a one-off mockup; the initial fixture contract is deliberately minimal and is refined by observed usability. B.1 is not a prerequisite for this isolated UI work.
2. **Complete activity and runtime contract.** Define stable course, pathway, chapter, knowledge-component, lesson-version, locale, asset and prerequisite identifiers. A learning objective can have different age-specific depth and examples without inventing a second mastery brain. The contract names client-safe activity data, server-only answers, canonical response state, scorer inputs, minimum supported client capability and recovery semantics. Build Appendix A's Core charts and 16 reusable interaction primitives and Appendix P's first-release math, logic and money visuals to the specified release scope. Client recomputation must be deterministic; the server independently verifies gradable responses. Every drag has tap and keyboard alternatives, every chart a table, every locale its prescribed number/currency/notation behavior, and no board decoration or unapproved celebration is introduced. Reconcile this with the repository's independent packages through executable parity checks; the SPEC's one pure scorer in browser and server remains the behavioral requirement.
3. **Pathway and credit model.** After B.1's placement acceptance, compute eligible next lessons from the shared knowledge graph/mastery/review-card model. Define progress and badge denominators for each eligible pathway and how mastery/credits transfer when a learner advances to another stage. Age safeguards follow age, not account role. The precise eligibility and equivalence policies below remain open; do not hard-code a guess.
4. **Mentor presence and experience.** Reuse the actual 3D models, Diorama and pose catalogue through the one stage component, compact inside the lesson per Bible 08. Keep answers visible in the first phone view; support captions, reduced motion and low-power fallback. The Mentor uses the same competence and visual vocabulary; the live Mentor redesign itself remains S06, with its privacy and governance gates.
5. **Pilot gate.** Author one representative lesson without bulk AI generation, including a decision, a manipulable visual, wrong-answer recovery, a short Mentor interaction and a full review/publish/version cycle in a disposable environment. Verify across age-appropriate variants, three locales, light/dark, narrow/wide layouts, accessibility, client/server scorer parity, stale-client refusal, reload, interrupted attempt and content revision. Pilot pass is evidence for the engine contract, not approval for catalog release.

## Phase B: Forge and catalog regeneration

1. Produce a coverage matrix for each principal course: competencies, prerequisites, misconceptions, age pathways, representations, lesson variants, review cards and placement probes. Include the fourth existing catalog in the migration inventory, then decide its place without silently deleting it. The final lesson count follows coverage and the Appendix C pedagogical criteria, not a fixed quota.
2. Extend Forge to author the new versioned contract and Appendix A/P representations, then run Appendix C's Stage 0–6 production pipeline: human competency scope, authoring, deterministic gates, named pedagogical review, real target-age usability pilot for new formats, instrumented release and post-launch recalibration. The behavior gate tests the entire permitted interactive input range, not one sample state. Copy, cognitive-load, narration redundancy, language, localization, safety, answer privacy and author/reviewer separation are enforced before publication.
3. Keep the current DeepSeek/Qwen roles until the later provider review decides otherwise. Use budgeted dry runs and a small evaluated sample before paid bulk generation. A model approval is never a substitute for the required human pedagogical review.
4. Build a legacy-to-new mapping by stable competencies and learning evidence. Reconcile placement, best scores, XP, badges, streaks and active attempts per learner before any cutover. Archive replaced lessons only after the new pathways pass acceptance and a rollback rehearsal. Preserve historical records and do not silently remap mastery from a weak or unrelated lesson.

## Critical decisions still open

These are **design questions, not implied owner approvals**:

1. Exact pathway bands and transitions, including whether a competent minor may access any older-stage material early and which adult examples remain adult-only.
2. The badge/progress contract: a badge for the eligible age pathway, staged credentials under one course, or a different formulation; how an earned badge survives a later catalog expansion.
3. Equivalence rules for old-to-new lessons and a learner aging into a new stage, including what placement credits demonstrate versus what needs a new diagnostic.
4. Publication policy for a revised live lesson: whether an active attempt is pinned to the started immutable version, and who approves a new version in an already published course.
5. The first pilot concept and the staff/content workflow that will author and review it.

## S05.1e: fail-closed completion on the existing server

**Product check against B.4.** The existing Core completion route previously used only answer-key entries as graded IDs. ## S05.2 boundary: authoritative v2 attempts and publication

**Verified legacy gap.** `lesson_documents` is keyed by `(lesson_id, locale)` and its document/answer-key row is mutable. Core's current GET and grade routes select that row afresh; grade accepts a segment ID and answer but no signed v2 attempt token or exact content version. The attempt row records `document_updated_at`, yet an in-place replacement can remove the content and rubric to which that timestamp refers. Completion recomputes against the current document's segment set and XP, not a saved immutable version. Neither the preview checkpoint nor this timestamp establishes the SPEC's active-attempt continuity. The legacy v1 fail-closed correction in S05.1e is valuable but does not solve this v2 boundary.

**Required implementation sequence before any published v2 pilot.** Create immutable document-version rows with separate server-only answer keys and an explicit current-version pointer; preserve existing lesson IDs and all historical evidence. Serve a versioned answerless document with the client's required-capability negotiation and an expiring server-signed attempt token bound to learner, lesson, locale, version, segment, seed and nonce. Atomically consume that nonce once for a scored semantic response; reject an impossible state before invoking the one pure scorer shared by browser and server. Record the immutable version and authoritative score. Completion reads only the versions and scored segments pinned to that run, even if a newer version has been published; it never trusts a client score. Define how a paused run resumes, expires or is reviewed after publication, and how an old client is refused without a false pass. Keep the v1 path intact until an explicit cutover and progress reconciliation.

**Acceptance evidence still needed.** Disposable-database tests must cover replayed/expired/tampered/wrong-user tokens, conservation and snap-grid rejection, server/browser scorer parity over the permitted input range, concurrent grade attempts, a publication between grade and completion, locale fallback, interrupted/reloaded runs, old clients and rollback. The migration requires the README's two clean database resets and generated-type check. Docker Desktop recovered, but its current stack contains local data and is not a disposable reset target. This checkpoint remains a design boundary, not a schema implementation or accepted server behavior. It does not authorize a production mutation. The first-release Appendix A/P catalog and owner-reviewed visual set still precede the Forge phase.
