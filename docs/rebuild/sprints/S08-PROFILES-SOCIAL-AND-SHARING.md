## S08.1 implementation and rationale

Inspected evidence: the public profile response derived `isTutor` from the bare `parent` role — a platform-wide trust signal visible to any signed-in user, including unconnected kid-role accounts, and it did not even require current verification. E.5's mandate is to restrict the badge to the verified adult's own linked children and connections approved through E.1's gates.

`tutorBadgeVisible(viewer, subject)` replaces the role check: the subject themself and staff viewers always see it; everyone else only when (a) the viewer is the subject's verified-linked kid (`guardian_links`), or (b) a mutual follow exists (the approved-connection form available to this surface), AND the subject's latest `parent_verifications` row is `verified` via `local-ocr` — aligning the badge with A.5's "verification must mean one thing". An ambiguous verification or link read hides the badge (fail closed: an absence is safer than an unearned trust signal). The public-profile route serves only the boolean; no new data reaches the client.

## S08.2 implementation and rationale

Inspected evidence: the share flow issued a permanent link with no disclosure of what it was (a public, instrumented acquisition touchpoint). F.2 has since added the 30-day expiry and per-share revoke, so the disclosure states the real mechanics instead of the SPEC's placeholder copy. A caption line sits directly under each Share button on the parent territory surface (streak and goal-reached): anyone with the link can open it, it expires in 30 days, it can be revoked from the Family panel, and it helps LittleFounders grow — mentor-voiced, not a liability disclaimer. The F.2 caching caveat (a messaging app may keep its own preview after revocation) is documented in the S02.4c record and remains a candidate for a deeper explainer, not a point-of-action caption.

## S08.3 implementation and rationale

Inspected evidence: `badge_shares.age_band` (vocabulary 6-8/9-11/12-14) was never populated. The share route now computes it from the kid's stored birth date (the same date math as the age screens) at issue time; a kid outside the teaching bands or without a date gets NULL rather than a guessed value. `getKidProfiles` gained `birth_date` for the server-side computation only — it is never a response field.

## S08.4 implementation and rationale

Scope: F.1 (architecture, per OD-20), F.3 (disclosure rewritten for the image flow), F.5 (brand position, reflected in copy and metrics), F.6 (standing constraints pinned), and the legacy-link retirement OD-20 requires (F.2 now governs legacy links only). The written policy, runbook and metric map are in [`docs/rebuild/policies/ACHIEVEMENT-SHARING.md`](../policies/ACHIEVEMENT-SHARING.md); the brand position is `docs/product-audit/COSMIC_NARRATIVE.md` §5.

**Inspected evidence (current state, not the SPEC's legacy description).** F.2 (S02.4c) had already added a 30-day expiry, per-link revoke with image purge and `noindex`, so the SPEC's "permanent, indexable" description was stale. What remained true: every share still minted a company-hosted public page plus a world-readable Depot image, a messaging app still built a rich preview from the Vercel function's Open Graph tags, the link carried `utm_campaign=badge-share`, the landing page counted strangers' visits (`badge_link_click`, anonymous), and an expired link whose page was never visited again kept its image world-readable forever (the purge only ran on revoke or on a visit). The Depot image's kicker was hard-coded Spanish, a goal label said "LF Coins", and long names or labels clipped off the 1080 px canvas.

**F.1 — image architecture (enforced at Core, Depot and the database).**
- Core `POST /api/v1/family/kids/:kidId/achievement-image` replaces the link issuer. It keeps every existing gate (verified adult parent, `guardKid`, server-side achievement verification), renders through Depot, re-checks `guardKid` after the reads, and returns the PNG in the response (`Cache-Control: no-store, private`, `Content-Disposition: attachment`, `nosniff`). It writes no `badge_shares` row, mints no token and returns no URL. The body is `.strict()`, requires the declared hand-off and refuses any client label, name, image or age field.
- The old `POST .../badge` answers 410 `SHARE_LINKS_RETIRED` before reading, rendering or storing anything.
- Depot `POST /api/v1/badges/render` returns bytes and writes nothing to storage. The old compose-and-store `POST /api/v1/badges` answers 410 and writes nothing, so even an outdated Core cannot mint a new public image. Core accepts only a real PNG under 8 MB and refuses (never substitutes) otherwise.
- Migration `close_badge_share_links` (contract) adds a BEFORE INSERT trigger that makes `badge_shares` refuse every new row from any role. It is declared contract because an older Core stores the image before inserting the row; applied early, it would strand a public image with no row to revoke or sweep. The migration-phase gate lists it as pending and auto-apply refuses it.
- Frontend: `rebuild/family/achievementImage.ts` is the client layer (hand-off chosen before the request with a probe `canShare({files})`, share sheet with a PNG file, download of a local object URL otherwise; a dismissed sheet is `cancelled`, never a failure or an unasked download; any other share refusal, such as an expired user activation, falls back to a download). The live territory page (legacy, no restyle) now calls it for both the streak and the reached-goal buttons; the `copied` state became `saved`.

**Legacy links (OD-20: keep F.2 until expiry, then retire the route).**
- Cutover `2026-09-24T00:00:00.000Z` (OD-20's date) and retirement `2026-10-24T00:00:00.000Z` (cutover + 30 days, when every legacy link has expired) live in `backend/src/services/badgeLinkWindow.ts`. A link is live only if issued before the cutover, un-revoked, inside its window and before retirement. A post-cutover row is never served and its image is purged.
- From the retirement date Core's public read answers 410 without a database read, the Vercel function answers 410 without calling Core, the landing page shows its not-found state without calling Core, and the Family list returns no links. Revoke stays callable until the dated removal.
- New internal `POST /api/v1/internal/badge-links/purge` plus daily `.github/workflows/badge-link-retirement.yml` purge the Depot image of every dead legacy link, closing the unvisited-expiry gap. Each run is audited (`badge_links.images_swept`, including zero-purge runs), an ambiguous twin-reference read never deletes, and a failed read is a 502, never a zero.
- The dated removal (delete the legacy code, then a contract migration dropping `badge_shares`, which also retires the legacy `age_band` column, and narrowing the event CHECK) is a written runbook in the policy, deliberately not a migration now: the table must keep serving legacy links until 24 October 2026.

**F.3 — disclosure for the image flow.** Two body lines directly under each Share button, bound with `aria-describedby`: "You get a picture with their first name. No link is made." / "Anyone you send it to can keep it. It shows LittleFounders." (es-MX and pt-BR equivalents in the policy). They name what is created, what is not, the part nobody can undo (this replaces F.2's third-party caching caveat, which no longer applies to new shares) and the brand exposure. They drop every expiry/revoke claim, because the image has neither. Each line fits the Copy Budget (12 words EN, 15 ES/PT, two sentences) in all locales, pinned by `previewCopy.test.ts`. The legacy-link panel now reads "Old share links" and says those links stop working on their date.

**F.5 — brand position, copy and metrics.** `COSMIC_NARRATIVE.md` §5 states what sharing is (a proud moment a parent chooses to send), what it deliberately is not (a public listing, a marketing use of a child, anyone's decision but the verified guardian's), its promises and why this is Law 2 and Law 5. The copy repeats it at the point of action. Metrics follow OD-20: migration `achievement_share_initiations` (expand; RLS on, no policy; no user, kid, name or image column) records one row per rendered image by kind and hand-off, and `GET /api/v1/admin/analytics/achievement-sharing` (view_analytics) reports shares initiated, the Persistent Public URL Rate (structurally 0) and the legacy lifecycle. Viewer reach is gone: `badge_link_click` is no longer recordable, the anonymous beacon drops it, the landing page tracks nothing, and the usage dashboard lists it as a retired event (the DB CHECK is narrowed at the dated removal). `sharing:check` is the Appendix L Brand-Narrative Coverage Check.

**F.6 — standing constraints.** Written in the policy (section 2) and pinned by `backend/src/__tests__/achievementSharingConstraints.test.ts`: direct requests from 13 refused populations (no session, parent-created under-13 kid, guest, independent teen, adult non-parent, parent unverified/revoked/other-method, minor with a parent role, kid+parent, staff admin, superadmin, unlinked verified parent), a guardian link revoked mid-request, five unearned achievements, client-supplied fields, the exact minimized Depot body (first name only) and the no-persistence invariant. Two mutations (removing the post-read `guardKid`, replacing `firstNameOnly`) were run and each failed the suite. `sharing:check` (now part of `spec:check`) pins the cross-service facts: date parity, no insert path, no stored image, the closing trigger, no viewer reach, the brand position and the policy text; its self-test proves each check fails on the regression it guards.

**F.4 under OD-20.** S08.3 populated `badge_shares.age_band`, but the new flow persists no entity, so there is no producer any more. The field is legacy-only and is removed with the table in the dated removal; the new `achievement_share_initiations` table has a producer and a consumer for every column. `shareAgeBand` was deleted as dead code.

**Image quality.** The renderer localizes its kicker line (it was Spanish in every locale), goal labels say coins/monedas/moedas per the glossary, long first names shrink to fit one line and long labels wrap onto up to four lines. The art itself (system-font emoji on a gradient) is still the legacy template; redrawing it as a house-style asset is a wave-2 design-system item.

**Proposals recorded for the owner (conservative defaults implemented).**
1. Cutover instant: OD-20 says links issued "before this decision" keep their controls. The cutover is 00:00 UTC on 24 September 2026, so a link minted later that day by the live platform is refused (fail closed). If the owner prefers the production deploy instant, only the constant and its two mirrors change.
2. The picture carries the LittleFounders name (the only growth element left). The disclosure says so. Removing the name from the image is a one-line renderer change if the owner prefers a brand-free picture.
3. The sweep is a scheduled production workflow; it starts running when the owner pushes and deploys this lane.

## S08.5 implementation and rationale

Scope: E.6, read with A.1 and component 5 of the Block E standard. The written policy, runbook, metric definition and open decisions are in [`docs/rebuild/policies/ACCOUNT-DELETION.md`](../policies/ACCOUNT-DELETION.md).

**Inspected evidence (current state).** The SPEC's description holds. The FAQ answered "Yes — contact us and we'll process the deletion under the Privacy Notice", and no self-service path existed. Reading the code found three deeper defects that a self-service button alone would have hidden:

1. **Some accounts could not be deleted at all.** Eight provenance columns referenced `auth.users` with NO ACTION or RESTRICT: `wallet_ledger.created_by`, `redemptions.decided_by`, `banking_accounts.opened_by`/`frozen_by`, `allowance_rules`/`savings_bonus_rules`/`spend_limits.parent_user_id` and `tutor_voice_consent.granted_by`. So any Tutor who had used the Family Hub or granted voice consent could never be deleted. The 0010 guards refused to delete a parent who was a child's last verified Tutor, so A.1's promise (parent account gone → child paused → purged after 90 days) could not start from a deletion.
2. **The deletions that did exist left data behind.** The Tutor's delete-a-child route and the 90-day purge both called GoTrue's user delete. That left the Mentor memory ledger (no foreign key by design), converted pre-signup visitor rows and their events, email logs, every Depot object (Mentor speech audio, task evidence photos, legacy badge images) and every warehouse row. A live Mentor session could keep writing back.
3. **Deletions left no trace.** There was no record of what was deleted, when, at whose request, or whether it finished.

**One lifecycle for every deletion (enforced in the database and Core).**
- Migration `account_deletion_requests` (expand) adds the request table (RLS on, no browser policy, even the service role writes only through the functions) and the service-only lifecycle: `request_account_deletion`, `cancel_account_deletion`, `claim_account_deletion` (ten-minute exclusive claim, stale-claim takeover, and a hold while an open E.3 safety-review case names the account), `record_account_deletion_step` and `complete_account_deletion`. Completion refuses unless the oracle, core, depot and dataintel steps are all recorded and no Depot path is left. Every state change audits in the same transaction. The migration also makes the eight provenance columns nullable with `ON DELETE SET NULL`: the child's record stays and the departed adult's id leaves it. It teaches the 0010 guards (and the kid-role, admin-grant and lesson-version guards) to accept exactly the changes an erasure in progress makes, and nothing else.
- Migration `account_erasure_function` defines `erase_account_data`, the database half of the erasure in one transaction. It takes the Depot and warehouse inventory before the rows that point at it disappear. It removes the non-cascading rows: memory ledger, converted visitors, and email logs by id or address. It then removes follows, blocks and guardian links while the account still exists, so their audit triggers fire and 0110 pauses a child who loses its last Tutor. It ends voice consent the account granted, clears the account from staff grants it made, and deletes GoTrue's audit entries and the `auth.users` row. Depot objects that another account still references are kept. The migration is declared contract only because the classifier sees `DELETE` in the function body, and its header says so. Applying it deletes nothing.
- `backend/src/services/accountDeletion.ts` runs the four steps in order, each idempotent and recorded: Oracle first, so no Mentor turn is written back after the rows are gone; then the Core transaction, Depot and the warehouse. A failed step is audited (`account.deletion_step_failed`) and resumed by the daily sweep. The Tutor's delete-a-child route (`family.ts`) and A.1's purge (`guardianLifecycle.ts`) now call `eraseNow`, so there is one path. The sweep lists due and stale requests before held ones, so a queue of safety holds can never starve a due erasure. That ordering was found and fixed during this checkpoint, and a test pins it.
- Oracle `POST /api/v1/tutor/erasure` (internal key) closes the learner's live socket and drops parked sessions without the ordinary endings: no close written back, no paid post-session review, no trajectory. Dataintel `POST /api/v1/intel/erasure` deletes the account's rows and its converted visitor ids' rows from the six raw tables in one transaction. It records tombstones that the sync re-applies after every run and forgets after 30 days.

**Self-service (Core `/api/v1/account/deletion`).** Eligibility is decided from roles, the age screen and the guest flag, never from the browser. A parent-created child gets 403 `KID_DELETION_BY_TUTOR` (its Tutor deletes it from Family). Staff get 403 `STAFF_ACCOUNT` (a superadmin removes staff; the database refuses too). A guest or a self-registered account whose age screen says under 13 is erased at once. Everyone else, including an independent teen 13 to 17, gets a 14-day grace period and every session is signed out. Confirmation is enforced by the server: the body is `.strict()` with `acknowledge: true`. A password session re-enters the password (a real GoTrue sign-in), an OAuth or link session must have signed in within 15 minutes, and the route shares the auth rate limiter. `/auth/me` reports a scheduled deletion. `DELETE` keeps the account and audits the cancellation. `GET` also tells a parent how many children they supervise alone; those children are paused when the erasure runs.

**Sweep, metric, standing guardrail.**
- `.github/workflows/account-deletion.yml` runs the internal sweep daily at 03:45 UTC and audits every run.
- `GET /api/v1/admin/analytics/account-deletions` (view_analytics) is Appendix J's Deletion-Request Clarity metric: requests by initiator and population, the stated-timeline rate, the within-SLA rate (48 hours after the stated date) and the open/overdue queue. It returns counts only and fails closed.
- `npm run deletion:check` (in `spec:check`, with an 11-case self-test) pins the facts that span packages: the route and its refusals, no direct GoTrue delete outside the audited rollback of a half-created child, the four steps, the memory-ledger erasure, the grace period and SLA in Core versus the policy, the FAQ in three locales, and the scheduled sweep.

**Surface (rebuilt, self-contained; legacy Settings not restyled).**
- `frontend/src/rebuild/account/` holds the client layer (`deletionClient.ts`, validated answers only) and `AccountDeletion.tsx`, one copy-driven component for every state.
- The intro states the timeline (days or "as soon as you confirm") and how to keep the account. "What gets deleted" is layered behind a native disclosure (Bible 06 §4) and says what stays. The confirm step shows the children who will be paused and their 90-day rule right above the decision. It needs the acknowledgement checkbox and, where Core asks, the password before the destructive button enables.
- Afterwards the public `/account-deletion` screen states the date and how to keep the account, or confirms the deletion. `RequireAuth` sends a signed-in account with a scheduled deletion there. That screen offers "Keep account" and "Sign out" and nothing else.
- The legacy Settings page mounts the block at its end. The FAQ answer states the self-service path and the 14-day timeline in three locales.
- Copy follows the Copy Budget and the glossary: "Tutor" is the verified parent, "Mentor" is the AI, and "coins" is never money. There is no celebration and no em dash.
- `accountDeletion.ts` was renamed `deletionClient.ts` because Windows' case-insensitive resolver matched `./AccountDeletion` to it.

**Proposals recorded for the owner (conservative defaults implemented).**
1. Grace period of 14 days and completion SLA of 48 hours after the stated date. E.6 leaves both open. Product owns the decision, which is due before release.
2. Legal copy is unchanged. The Privacy Notice should state backup retention, and counsel should read the Terms' retention paragraph against the policy.
3. An independent teen's deletion notifies nobody, since no guardian exists in that flow.
4. An account under an open safety review is held rather than erased, because the evidence cascades away with the account. The holder can still keep the account.

## S08.6 implementation and rationale

Scope: E.8 (age-tiered social layer), E.9 (the follower/following count as a comparison metric) and E.13 (what an approved or earlier viewer can still use to find a child off-platform). E.5's leak in follower lists was found and closed during the E.13 audit. The written policy, field audit, runbook and open decisions are in [`docs/rebuild/policies/SOCIAL-TIERS.md`](../policies/SOCIAL-TIERS.md).

**Resume note.** This checkpoint was started by an agent that hit its usage limit. The worktree was clean when work resumed: S08.5 had been committed at 00:12 and no S08.6 change had been written. Nothing needed to be kept or discarded.

**Inspected evidence (current state, not the SPEC's legacy description).** S02 had already built E.1's strictest tier for inbound connections to a `kid`-role account (non-discovery, guardian approval, audit, reporting). What remained true:

1. **The tier followed the role, not age.** A self-registered 13 to 17 year old was treated exactly like an adult: public, followable by anyone, listed in anyone's followers. A guest or an unscreened account had a full social layer, although OD-3 gives guests none.
2. **A child could loosen its own tier.** A `kid`-role account could follow any adult it could reach by username. No guardian was involved.
3. **Counts were everywhere.** Both profile routes counted followers and following, and both legacy pages showed them as stat tiles in the same grid as XP, streak, lessons and minutes. This is exactly what E.9 names.
4. **Nothing reviewed profile content.** A child's handle or display name could carry a school, a street, a phone number, another platform's handle or a birth year. The kid-creation test fixture itself used `sofia_2016`. A minor's last-active date was served to any viewer.
5. **E.5 leaked through lists.** Follower and following cards set `isTutor` from the bare `parent` role. That is the platform-wide trust signal S08.1 removed from the profile itself.

**E.8: one tier per account, decided by the database.**
- Migration `social_age_tiers` (expand) adds `public.social_tier`. From service-owned evidence, in order: `kid` role → guardian; an under-13 origin that a verified guardian linked → guardian; an unlinked under-13 origin, a GoTrue anonymous user, an account with no role or no age screen → closed; a parent with current 18+ ID verification → adult; the age-screen band then decides adult or teen. An unreadable tier is no access in Core and a refusal in the database.
- The same migration adds the teen's own consent queue: `social_consent_requests` (RLS on, no browser policy, service role read-only) and the functions `request_teen_connection`, `decide_teen_connection` and `has_current_teen_consent`. These take the pair lock every other social transition takes and audit every step with `tier: 'teen'`. A child cannot initiate a request. A requester holds at most 20 pending requests, and a declined requester waits 30 days to ask the same teen again.
- Migration `social_tier_enforcement` (contract, applied after the Core release) replaces the follow admission trigger. Into a teen, only the teen's accepted consent (`SUBJECT_CONSENT_REQUIRED`). Out of a child, only its family or an account its guardian already approved (`GUARDIAN_MANAGED_CONNECTIONS`). Nothing to or from closed (`SOCIAL_TIER_CLOSED`). No new outside connection for a flagged minor (`PROFILE_REVIEW_REQUIRED`). The E.1 guardian rule is unchanged. It also replaces `social_subject_visible`, the browser-side rule behind the follows RLS policy, with the same tier logic. The block and unfollow functions now also close teen consents, and `remove_social_follower` lets the account being followed remove a follower.
- Core: `socialTier.ts` calls these functions. `socialVisibility.ts` returns full, card or none by the subject's tier (policy §1). The private teen resolves to a card: handle, cartoon avatar and cover preset only. New routes: `GET /api/v1/profile/connection-requests`, `POST /api/v1/profile/connection-requests/:id/decision` and `DELETE /api/v1/profile/followers/:username`. Each binds the teen to the session. `POST /profiles/:username/connection-request` routes a child's request to its guardian and a teen's to the teen (`decidedBy`), and `POST /follow` refuses by tier. The profile response carries a `connection` mode, so the page never guesses.
- Surfaces (rebuilt, self-contained): `rebuild/social/PrivateProfile.tsx` (the private card, and the child's "your Tutor handles your connections" line), `TeenConnections.tsx` (requests with Accept/Decline, followers with Remove, no counts) and `teenConnectionsClient.ts` (validated answers only). The legacy public profile renders the card or the full profile from Core's verdict and shows Follow only when the mode allows it. The legacy own profile mounts the teen panel for a teen.

**E.9: removed, not opt-in.** Core emits and queries no count. The two legacy pages replaced the count tiles with unnumbered "Followers" and "Following" links in their own row, outside the stats block (the stats grid is now four tiles). `social:check` automates Appendix J's Comparison-Metric Audit, and its self-test proves both regressions fail.

**E.13: audit, review and containment.**
- Audit: every Core surface that returns profile data is listed field by field in policy §3.1, with a verdict and a fix. Two exposures were found besides the named fields: a minor's last-active date (now withheld from everyone but the minor) and E.5's list leak (now each card applies E.5's relationship rule).
- Review: `public.profile_field_flags` and Core's `profileFieldFlags` apply the same seven rules (contact, link, handle, platform, school, location, birth year). They share a 43-case corpus that runs against both. `social:check` compares every pattern literally. Accented letters are matched with `.`, so the result does not depend on the database collation's `lower()`.
