## Why it ran from the operator's machine

GitHub Actions stopped starting jobs at about 12:56 UTC with *"recent account payments have failed or your spending limit needs to be increased"*. Every CI, CD and cutover workflow runs there, and so do the scheduled jobs, including backups.

The owner ordered the deploy anyway and authorized, in the session, running it from this machine:
- registering the machine's SSH key `lf-owner-laptop-cutover` on the Railway account;
- generating the backup key locally;
- deploying the services with the Railway CLI;
- deploying the frontend with the owner's Vercel login.

Every database step reused the exact SQL and checks of `cutover.yml`, run through Railway SSH. The local copies of the tools are in `%LOCALAPPDATA%\Temp\lf-ops` on that machine.

## Rehearsal (before production was touched)

GitHub Actions restored a production dump (45 MB) into a disposable database with the same image on a runner, and replayed the whole window there. Run `36714913218` showed:

- All 174 migrations applied to real data with no failure.
- The freeze refused service-key writes, while the window token could still write.
- The OD-9 toolkit ran as a dry run, then applied, then applied again.
- Reconcile: 52 of 52 families unchanged.
- The backup restored and matched the before inventory.

The rehearsals found eight defects in the cutover mechanics, all fixed before production:
- The backup key was missing.
- The runbook's freeze did not stop PostgREST writes. It was replaced by a PostgREST pre-request function.
- Phase errors were masked.
- `pg_restore` failures were not reported.
- Production role names were missing on the copy.
- The token mask corrupted the token.
- The smoke read used the anon key.
- PostgREST's schema cache was stale after the migrations.
