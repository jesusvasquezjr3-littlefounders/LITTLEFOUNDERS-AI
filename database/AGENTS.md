# AGENTS.md — database (Vault)

> Domain rules for this service. Root rules: [/AGENTS.md](../AGENTS.md). Context: [agent/core/CONTEXT.md](../agent/core/CONTEXT.md).

## Mission

The schema of record: migrations, RLS policies, seeds, and the generated TS types every service consumes. Deploys as **Supabase self-hosted on Railway** (runbook: [DEPLOYMENT.md](DEPLOYMENT.md)).

## Migration protocol (non-negotiable)

1. Sequential `NNNN_description.sql` — no gaps, no duplicates (`npm test` gates this).
2. **Never edit an applied migration** — write a delta migration.
3. Idempotent DDL: `IF NOT EXISTS` everywhere.
4. **RLS in the same migration** as every `CREATE TABLE` (`npm test` gates this).
5. The local runner records every applied file in `public.schema_migrations`
   with its SHA-256 checksum. It applies a new file and its receipt in one
   transaction, refuses checksum drift, and never replays a recorded file.
   A legacy database without the ledger must be independently inspected and
   baselined once via `npm run db:migrate -- --baseline NNNN`; never infer a
   high-water mark and never replay historical migrations over it. The
   operator runner (`scripts/railway-migrate.sh`) sends the remote pipeline
   as ONE positional argument and judges success from psql OUTPUT (a
   trailing sentinel plus the absence of `ERROR:`) — the Railway CLI does
   not propagate the remote exit status, so exit codes prove nothing. A
   `--baseline` request must additionally pass a read-only signature-object
   probe (data-driven map in the script; evidence in DEPLOYMENT.md). All of
   this is covered by the local no-write integration test in
   `scripts/railway-migrate.test.mjs`.
6. Verify locally: `npm run db:reset` twice — both must succeed (or use an
   isolated disposable stack; never nuke a shared development database).
7. Regenerate types after schema changes: `npm run db:types` → commit `types/database.ts`.
8. Applying anything to production is a BOUNDARIES action — human sign-off first.

## Invariants owned here (DB-level enforcement of /AGENTS.md §1.3)

- 6-role CHECK on `user_roles.role`; superadmin `@littlefounders.ai` trigger.
- Families = `family_members` join table (multiple parents by construction).
- `guardian_links.verification_status` — only Guardian-driven flows move it to `verified`.
- `audit_logs` append-only: no UPDATE/DELETE policies, ever (`npm test` gates this).
- Signup bootstrap (`0003`): every `auth.users` INSERT auto-creates a profile + grants `universal` (§1.4 default role). Role grants/revokes are audited into `audit_logs` by trigger.
- Profile identity (`0005`): `profiles.username` (unique, `^[a-z0-9_]{3,20}$`), `profiles.cover` = jsonb PRESET config and `avatars.options` = DiceBear option sets — **no image/binary storage exists for covers or avatars, NON-NEGOTIABLE**. `follows` edges are self-managed via RLS (you only write rows where you are the follower); public exposure of profile fields happens ONLY through Core's whitelisted endpoint, never by loosening profiles RLS.
- `0002_content_skeleton.sql` is **PROVISIONAL** — its `lessons` table was superseded by `0007_course_hierarchy.sql`'s real hierarchy (`courses → adventures → sagas → topics → lessons → lesson_documents`, COURSE_ENGINE.md §2); `courses` itself was kept and extended, not dropped.
- `lesson_documents` (`0007`) has **NO RLS SELECT policy at all, by design** — RLS is row-level, not column-level, so any policy that exposed the row to authenticated clients would also expose `answer_keys` (server-only) sitting right next to the client-safe `document` on the same row. Zero permissive policies = deny to `authenticated`/`anon`; only the service role (Core, which bypasses RLS) may read this table, and Core is responsible for stripping `answer_keys` before serving `document` to a browser. Never add a client SELECT policy here — split the answer key out of the table first if that ever needs to change.
- Production course release (`0031`): `course_release_verifications` is service-role-only, RLS-with-zero-policies operational metadata. Forge writes it only after a successful full `verify:course`; `release_course(course_id)` is service-role-only and is the sole production bulk-release path through Core. It locks the hierarchy, rejects missing descendants, non-review-ready lessons, incomplete three-locale documents, and verification older than the latest document update, then publishes the entire hierarchy atomically. `scripts/publish-course.sh` is local-development-only and must never become a production bypass.
- Illustration style provenance (`0032`): `lesson_documents.illustration_style_version` records the Forge visual identity used for the stored media. `NULL` is legacy/unknown and is never eligible for Forge's zero-cost image inheritance; a style bump therefore cannot silently reattach obsolete art to a new release.
- Game feature retirement (`0033`): the never-shipped `games`, `game_documents`, `game_attempts` and `game_progress` tables, the `learning_events.game_id` column, and game event/route vocabulary are removed by a forward-only delta. Historical migrations `0027`–`0029` remain immutable audit history; no active service or production route may depend on them.
- `adventures.age_tier` (`0007`, widened `0008`): `tier1` | `tier2` | `tier3` — tier3 (ages 10-12) is reserved for the Inversiones course only (COURSE_ENGINE.md §3.1b); `courses.requires` (`0008`) is the course-level prerequisite edge, a jsonb array of prerequisite course slugs.
- Spaced-review projection (`0016`): `topics.kind` + `topics.review_of` (raw catalog slug paths, resolved at query time) are persisted by coursegen's publish — the catalog stays the source of truth. The `admin_retention_*` functions are the always-on retention instrument; EXECUTE is revoked from client roles, only Core (service role) may call them.
- Generation caches `picture_assets` (`0014`, Prism) and `speech_assets` (`0015`, Echo): service-role-only posture — **RLS enabled with ZERO policies, on purpose**. Browsers never read these tables (they get plain public Depot URLs embedded in lesson documents/manifests); only the owning service writes. Both guarantee "an identical paid-API request never pays twice" via a unique request-hash column; the asset BYTES live in Depot, these rows only map request → asset.
- Generation telemetry (`0017`): `generation_runs` / `generation_slots` / `generation_tracks` — coursegen's durable scoreboard (per-run summaries, per-slot outcomes with judge rubrics and failure stages, track reports). Same service-role-only posture as 0014/0015: RLS enabled, ZERO client policies; coursegen writes (swallow-on-failure ingest), Core's staff console (`/api/v1/admin/generation*`) is the only reader. Telemetry, never control flow — no pipeline behavior may ever depend on these rows.
- Generation live heartbeat (`0018`): `generation_runs_live` — per-run heartbeat upserted on every slot stage transition DURING active generation runs (active/completed/failed counts, stage breakdown, cost, images). Complement to 0017's post-mortem view; deleted when the run finishes; rows stale >2 min are ignored (the run process died). Same service-role-only posture; Core's `GET /api/v1/admin/generation/live` is the only reader.
- Generation Realtime (`0019`): SELECT RLS policy on `generation_runs_live` for admin/superadmin — the ONLY client-accessible policy on generation tables. Necessary but NOT sufficient for push-based live monitoring: the publication half landed in `0022`. Table carries zero PII.
- Heartbeat snapshots (`0020`): `generation_heartbeat_snapshots` — time-series record of every heartbeat update saved as a row. Used by the admin dashboard to render a run's progress curve over time (timeline chart). Same service-role-only posture as 0017/0018.
- Email logs (`0021`): `email_logs` — transactional email audit trail (id, message_id, to_address, subject, template_type, locale, user_id, status, detail jsonb, created_at; indexes on created_at DESC, status, to_address). Service-role-only posture like 0014/0015/0017: RLS enabled, ZERO client policies. **TWO writers, both Courier** (`email-server/src/db/emailLogsRepo.ts`, service-role PostgREST): `POST /api/v1/send` for mail we dispatch, and `POST /api/v1/logs` for mail the Haraka `log_delivery` plugin captures on `hook_queue_ok` — GoTrue's auth mail is submitted over SMTP :587 and never touches the HTTP API, so that second writer is the only path by which the platform's real mail is recorded. Unlike 0017/0018/0020, **Core is NOT the reader**: it proxies Courier's `GET /api/v1/logs` (`/api/v1/admin/emails/*`), so Courier holds the only service-role key for this table. The in-process ring buffer is a development fallback when `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are unset; a configured Vault outage must return `DATA_UNAVAILABLE`, never partial production history.
- **Nullable FK columns: write NULL, never a best-effort value.** `email_logs.user_id` references `auth.users(id)`, and PostgREST rejects the ENTIRE row on a violated FK — so a writer that passes an unvalidated identifier through loses the whole log line, not just that column, and loses it silently on a fire-and-forget path. Every writer of a nullable FK'd column must validate the value and fall back to NULL (`emailLogsRepo.ts` UUID-tests `user_id` before insert). This is the rule for all such columns here, not a one-off note about email.
- Realtime publication (`0022`): a SELECT policy authorizes a subscription but emits nothing on its own — Supabase Realtime reads Postgres LOGICAL REPLICATION, so a table is also a member of the `supabase_realtime` publication or the client stays connected, authorized and silent forever (verified on the production Vault: the publication existed with ZERO tables). `REPLICA IDENTITY FULL` is required, not optional, when the subscription listens for DELETE or the table has RLS: the default identity ships only the primary key, and Realtime re-evaluates the policy against the replicated row before forwarding it. **Enabling Realtime on a table is therefore TWO steps (policy + publication), and the table must carry zero PII (§1.9) because the full row is replicated.**
- Dataintel sync (`0026`): `dataintel_sync_state` cursor table (one row per source table, service-role-only, RLS with zero client policies) + 5 sync views (`dataintel_events_sync` — incremental event feed ordered by `event_id` for `gt.` queries; `dataintel_users_sync` — user dimension from `auth.users` + `profiles` + `learning_stats`; `dataintel_lessons_sync` — published lessons with segment count from `lesson_documents` JSONB; `dataintel_sessions_sync` — session summaries with a rolling 90-day window). All views are `REVOKE ALL FROM public, anon, authenticated; GRANT SELECT TO service_role`. The events view is the only incremental feed — the sync worker filters `event_id=gt.<last_event_id>` via PostgREST query params and advances `dataintel_sync_state.last_event_id` after each batch. Users, lessons, and sessions are full-refresh dimensions pulled once per sync cycle. **Standard PostgreSQL has no `MIN`/`MAX` aggregate for `uuid`** (verified against 17.6 — `function min(uuid) does not exist`; only reproduces once the migration is actually applied, not in any static review), which `dataintel_sessions_sync` hit picking a representative `user_id` per session: cast through `::text` for the aggregate, then back (`MIN(user_id::text)::uuid`) — fine here since a session has at most one `user_id` in practice, so the aggregate only needs A non-null value, not a true minimum.

- Insights depth + scale (`0024`/`0025`): `learning_events` gains `session_id`/`ordinal`/`device`/`locale`/`referrer_class` and an anonymous identity (`anon_id` → `anon_visitors`, first-party cookie); exactly one of `user_id`/`anon_id` is required by CHECK. **Five traps are load-bearing here.** (1) There is NO index on `(created_at::date)` and there cannot be — a timestamptz→date cast is not IMMUTABLE; filter on `created_at` and let the rollup own day-grained aggregation. (2) The rollups are accumulating TABLES, not materialized views: a matview is fully recomputed from its source, so the first refresh after the retention prune silently erased the pruned days from history. `refresh_insights_rollups()` rewrites only a trailing 7-day window and freezes everything older. (3) Dimensions coalesce to `''` rather than NULL so the primary key is total — NULL never equals NULL, so a nullable key column permits duplicate rows. (4) EVERY catalog DROP form here is asymmetric and raises rather than no-opping against the wrong kind: `DROP VIEW` on a matview, `DROP MATERIALIZED VIEW` on a view, and `DROP FUNCTION` on a procedure. `insights_daily_activity` has been all three shapes, so 0025 inspects `pg_class.relkind` and uses `DROP ROUTINE` — a fixed order aborts on exactly one of the possible starting states. (5) `prune_learning_events` is a PROCEDURE and carries NO `SET search_path` clause: a plpgsql FUNCTION cannot COMMIT (so its batching held one giant transaction), and Postgres also forbids transaction control in any routine with a SET clause. Every reference inside it is schema-qualified instead. Never sum `insights_daily_activity.users` — it is a count-distinct per dimension combination; `insights_daily_users` (role `''` = all roles) is the additive-safe answer. Retention is executable and audited: `CALL prune_learning_events(400)` + `refresh_insights_rollups()` run nightly from `.github/workflows/insights-maintenance.yml`, writing to `insights_maintenance_log`. The event enum contains ONLY events real code emits — a declared-but-unwired event is how a dashboard silently shows an empty series.
- Learning insights (`0023`): `analytics_consents` + `learning_events` + three `insights_*` views (/INSIGHTS.md is the spec). The §1.9 posture is STRUCTURAL: `learning_events` has NO jsonb payload and NO open string column — `event` and `route_class` are CHECK-constrained closed enums, `value` is numeric, `segment_id` is length-capped — so nothing a child types can enter the stream; widening this schema is a §1.9 review, not a routine delta. `analytics_consents` is the parental gate and an APPEND-ONLY LEDGER, not one row per kid: revocation closes the open row by setting `revoked_at`, and a re-grant INSERTS a new one. Upserting instead (the first design) rewrote history, leaving data already collected under a lawful grant with no evidence of the consent that covered it. "Was consent active on date X" must stay answerable for every X. Both tables are RLS-with-zero-policies (Core service-role only). The views run with OWNER privileges by necessity (the base tables have no policies), so client roles are cut off by explicit `REVOKE` — a new view over these tables MUST repeat that revoke or it becomes a client-readable RLS bypass. `learning_events.lesson_id` deliberately has NO FK: lessons are deleted/recreated on republish and history must survive restructures. Growth: append-only and unbounded — the ~400-day prune delta (INSIGHTS.md §6) is due before any large-scale rollout.
- Learning-intelligence contract (`0036`): event retries are deduplicated by `client_event_id`; optional client occurrence time is bounded at Core and preserved only for lateness monitoring. Attempts retain only closed pedagogical context (course/topic/skill IDs, time, document version and diagnostic code), never answer text. `dataintel_events_sync` and `dataintel_attempts_sync` expose these fields to the read-only warehouse. The migration continues the service-role-only view pattern and does not relax guardian consent for kid browser telemetry.

## The pinned Supabase stack (NON-NEGOTIABLE)

Local dev and production run the **official self-hosted stack from a clone of
`supabase/supabase` pinned in [`SUPABASE_VERSION`](SUPABASE_VERSION)** — always
the latest functional/approved release. `npm run db:sync` materializes the
clone at `database/supabase/` (gitignored; blobless sparse checkout of
`docker/`). Upgrades: bump the pin → sync → reset-twice + `npm test` →
update the DEPLOYMENT.md pin table in the same commit. Never run `latest`
tags; never edit files inside the clone (they're upstream's).

## Local dev

Requires Docker (and the Supabase CLI only for `db:types`). First run of
`npm run db:up` creates `supabase/docker/.env` with generated secrets
(gitignored) and email autoconfirm ON (local has no SMTP). Then:
`db:migrate` / `db:seed` / `db:reset` (from-zero: nuke → up → migrate) /
`db:types` (regenerates `types/database.ts` through the Supavisor pooler).
Studio: http://localhost:8000 (credentials: `supabase/docker/.env`).
Seeds: `seeds/dev_seed.sql` (dev only, never prod).
